\section{Introduction}

This document is the hazard analysis for \progname{}. \progname{} splits a
large language model (LLM) into blocks of layers and runs each block on a
different device on a local network, so that the devices can run a model
together that none of them could run alone. The leader node's coordinator assigns
blocks of layers to the devices and accepts prompts from the user. Each
follower node runs its block and passes the result on to the next
device.

\subsection{Definition of a Hazard}

For this document, a hazard is a state or condition of \progname{}
that, combined with conditions in its environment that the system does not
control, can lead to one of the losses listed in
Section~\ref{SecLosses}. Examples of such conditions are a device losing
power, a congested network, or an untrusted device on the same network. For
example, a device being assigned more layers than its memory can hold is a
hazard, and the crashes that follow are the loss. A failure mode is a
specific way a component can fail, and it can create a hazard.

\progname{} has almost no potential for physical harm, so its hazards are
mainly about privacy, security, the correctness and availability of
responses, and the effect of the system on the user's own devices.

\section{Scope and Purpose of Hazard Analysis}

\subsection{Purpose}

The purpose of this analysis is to find the ways \progname{} can cause a loss
while the project is still in the requirements phase, when a hazard can be
removed by changing a requirement instead of the code. Each hazard found in
the FMEA leads to a safety or security requirement, which is added to the SRS
and then verified through the V\&V Plan.

\subsection{Scope}

\noindent\textbf{In scope:}
\begin{itemize}
  \item The software components of \progname{}: the coordinator, the model
    partitioner, the inference engine on each device, the communication
    between devices, and the user interface.
  \item The interaction of these components with the user's devices, the
    local network that connects them, and the model files that are loaded.
\end{itemize}

\noindent\textbf{Out of scope:}
\begin{itemize}
  \item The content the model generates. Harmful, biased or false
    text produced by a correctly running model is a property of the model,
    which the user chooses and \progname{} treats as an input. Incorrect
    output caused by \progname{} itself is in scope.
  \item Defects in the operating system, drivers or GPU hardware. These are
    outside \progname{}'s control, so this analysis does not try to prevent
    them. It does cover their effects, such as a device crashing partway
    through a request, because \progname{} must respond to them.
  \item Attackers outside the local network, and physical access to a
    device. \progname{} is not exposed to the internet, and a person with
    physical access to a device already controls everything on it.
\end{itemize}

\label{SecLosses}

\section{System Boundaries and Components}

\subsection{Coordinator}
\label{subsec:coordinator}
This component exists on all nodes, but the following responsibilities are only run on the leader node:
\begin{itemize}
	\item Providing an OpenAI-API compatible API to the user for use with tools like
		\href{https://opencode.ai/}{OpenCode}.
	\item Tracking cluster health, and detecting node failures.
	\item Notifying nodes of partitioning changes.
	\item Rebuilding the cluster and saving in-progress requests
		in the case of node failure, removal, or addition.
	\item Measuring node connection performance.
\end{itemize}
On a follower node, it is primarily responsible for managing the inference engine
on its device, following the instructions of the leader node.

\subsection{Model Partitioner}
This component determines how to partition the model among the participating devices. It
decides at which points to cut the graph, how large each partition is, and which device gets
each partition. This component is integral to ensuring that each device is assigned an appropriate
partition given the device's computational and networking performance.

\subsection{Inference Engine}
This component is the high-performance inference engine running on each device. It will handle
execution of the given model partition for each device. It will call into
\href{https://github.com/ggml-org/ggml}{ggml} using the Rust-to-C FFI (TODO: glossary) to control the execution of a
device's model partition.

\subsection{Tensor I/O}
This component handles the compressing, sending, receiving, and decompressing of tensors between devices.
It will leverage \href{https://grpc.io/}{gRPC} for high-performance communication, with the potential
to use a custom solution should \href{https://grpc.io/}{gRPC} fail to meet our requirements in practice.

\subsection{Boundaries}
The system boundaries for Lake primarily consist of:
\begin{itemize}
	\item The \hyperref[subsec:coordinator]{Coordinator's} OpenAI-API compatible API.
	\item Model files (GGUF) loaded from disk.
	\item Networking components between devices (Thunderbolt, Ethernet, Wi-Fi, routers).
	\item The OS and GPU resources on each individual device.
\end{itemize}

\section{Critical Assumptions}
\label{SecAssumptions}

We assume:
\begin{itemize}
	\item The model file (GGUF) provided to Lake is already a functional LLM before partitioning.
	\item User requests are only made through the API on the leader device.
	\item Only one model will be run by the pool at a time.
	\item The local area network connecting the devices is private, and trusted by the user.
\end{itemize}

\section{Safety and Security Requirements}
\label{SecSafetyReqs}

\begin{itemize}
    \item \label{SR0-1}\textbf{SR0-1} -- The system shall identify and discard stale device health data from determining device availability by configuring a time-to-live for valid data. 
    \item \label{SR0-2}\textbf{SR0-2} -- The system shall only route inference requests to nodes that currently have a confirmed model layer partition.
    \item \label{SR1-1}\textbf{SR1-1} -- The system shall assign at least two nodes for model layer partitioning during distributed inference.
    \item \label{SR1-2}\textbf{SR1-2} -- The system shall ensure all model layers are assigned to a node, and that each device configured to run model layers receives a non-zero model layer partition assignment.
    \item \label{SR1-3}\textbf{SR1-3} -- The system shall reject models and layer allocations that are estimated to exceed the memory capacities of the Lake network or individual nodes, including a configured safety margin. Related SRS requirements: FR.S.2.1, FR.S.2.2.
    \item \label{SR2-1}\textbf{SR2-1} -- The system shall attempt an automatic bounded recovery and retry on inference requests if a follower node fails during inference. If the follower node is unable to be recovered within the configured recovery limits, the system must report to the API that the request has failed. Related SRS requirements: FR.S.1.10, FR.S.1.11, FR.S.1.13.
    \item \label{SR3-1}\textbf{SR3-1} -- The system shall identify corrupted and incomplete tensors throughout the distributed inference with integrity checks and communication timeouts to discard affected data and retry requests.
    \item \label{SR3-2}\textbf{SR3-2} -- The system shall log failed tensor decoding metadata and report a failure to the coordinator so the inference request can recover, subject to SR5-2.
    \item \label{SR4-1}\textbf{SR4-1} -- The system shall configure a timeout for communication between nodes, and handle exceeded timeouts according to the appropriate recovery or failure policy.
    \item \label{SR4-2}\textbf{SR4-2} -- The system shall mark a node as unavailable for inference or model layer partitioning when the node health criteria are not met, and require a successful health check before marking the same node as available. During a leader node failure, follower nodes shall detect and initiate a shutdown. Related SRS requirements: FR.S.1.24 and FR.S.1.25.
    \item \label{SR4-3}\textbf{SR4-3} -- The system shall utilise configured values or historical data to determine a baseline inter-node communication latency and notify the coordinator when that baseline is exceeded by a specified tolerance.
    \item \label{SR5-1}\textbf{SR5-1} -- The system shall require user approval on the leader node to authorise a follower node, and user confirmation on the follower node to confirm the authorisation before it can participate in the Lake network. Related SRS requirements: FR.S.1.17, FR.S.1.18, FR.S.1.20, FR.S.1.21, NFR.S.12.
    \item \label{SR5-2}\textbf{SR5-2} -- The system shall not record prompts, responses, tensor data, and KV cache content in diagnostic logs. Related SRS requirements: NFR.S.10.
\end{itemize}

\section{Roadmap}
\label{SecRoadmap}

Every safety and security requirement in Section~\ref{SecSafetyReqs} is tied
to a hazard in the FMEA, and each is scheduled below against the project
milestones from the Development Plan. The order follows one rule: a
requirement is implemented in the same phase as the capability whose failure
it guards. Without that capability the hazard cannot occur, and with it the
hazard is live, so the guard cannot wait for a later phase. Requirements
that guard a capability outside the capstone scope are deferred, and the
reason is given.

The thresholds in these requirements (the memory safety margin in SR1-3,
the time-to-live in SR0-1, the timeouts in SR4-1, and the latency tolerance
in SR4-3) are set to conservative values first and tuned from measurements
on the team's own machines before each demonstration. The values and how
they are verified are recorded in the V\&V Plan.

\subsection{After the capstone}

The following are known hazards or mitigations that the capstone timeline
does not cover. Each is listed with the condition under which it would move
into scope.

\begin{itemize}
  \item \textbf{Encryption between nodes.} The critical assumption in
    Section~\ref{SecAssumptions} is that the local network is private and
    trusted, which is also the Problem Statement's stretch goal. Hazard H5
    in the FMEA covers an untrusted node and data left on intermediary
    devices, and SR5-1 and SR5-2 handle both by user approval and by
    keeping request data out of logs. Neither stops a device that is
    already on a hostile network from reading or injecting tensors in
    transit. A potential user we interviewed for the SRS, who runs an
    on-premises assistant on export-controlled data, named encrypted
    traffic and company-managed machines as conditions for deploying
    anything like Lake. If the stretch goal is taken on, the assumption is
    removed, that hazard gets an FMEA row, and encryption and
    cryptographic node authentication become requirements.
  \item \textbf{Backing off when a device owner is working.} Loss L4 covers
    a device that becomes unusable because of Lake. The current
    requirements limit memory use (SR1-3) but do not pause or throttle
    inference when the owner is active. The interviewee's first condition
    for pooling office machines was that Lake back off the moment the
    owner starts working. This becomes a requirement once Lake is run on
    machines that are not dedicated to it, which is after the capstone.
  \item \textbf{No telemetry, and auditability.} The same interview asked
    that Lake send nothing outside the cluster, including usage or crash
    reports, and that its behaviour be auditable. The SRS privacy
    requirement (NFR.G.4.1) states that no request data leaves the cluster
    and that Lake sends no telemetry; it is verified by a network capture
    during a session, and SR5-2 keeps request data out of the logs that
    stay on the devices. Auditability has no requirement yet and is
    deferred with the encryption work above, since it matters for the same
    organisational users.
\end{itemize}

    the SRS safety requirements, but the FMEA also needed the SRS component
    list and the critical assumptions to exist first. We handled it by
    writing the SRS component section first and reusing its names and
    numbering here, and by opening one pull request per section so that a
    section could be reviewed as soon as it existed rather than waiting for
    the whole document. The second pain point was the FMEA table itself: a
    seven-column table that has to break across landscape pages is awkward
    in LaTeX. Ethan used an AI tool for the table formatting only, which is
    recorded in the disclosure.

    \item Two of the risks were on paper before this deliverable. The
    Development Plan's proof of concept section names network overhead
    making the split slower than a single device (H4-3), and the Problem
    Statement's dynamic allocation goal is built around devices dropping
    out of the pool mid-session (H2-1). A block larger than a device's
    memory (H1-3) was implicit in how the Development Plan describes the
    partitioner, but had not been written down as a failure. The rest came
    out of the FMEA. Walking the
    coordinator's responsibilities one at a time produced H0-1 and H0-2,
    stale health data and a missed partition notification, which we had
    not thought of because we had been picturing the happy path where every
    message arrives. The partitioner rows H1-1 and H1-2 came from asking
    what a correct partition even is, which forced us to write down that
    every layer is assigned exactly once and every node gets a non-empty
    block; that definition is now also the formalisation in the SRS. The
    Tensor I/O rows H3-1 and H3-2 came from the question of what happens
    when a message arrives but is wrong rather than missing, which is a
    different failure from H4-1 and needs a different check. The privacy
    rows H5-1 and H5-2 were added while the FMEA was under review. The SRS
    already said that untrusted devices must not join a cluster and that
    request data is not saved, but neither had been written down as a
    hazard, and a review comment moved H5-2 from node approval, which H5-1
    already covers, to data left on devices that are already in the pool.
    Finally, the
    user interview for the SRS, which happened during this deliverable,
    added two items to the roadmap that no one on the team had listed:
    backing off when a device owner is working, and sending no telemetry.

    \item Two other types of risk matter for Lake. The first is privacy and
    security risk: a software product can leak data without anything
    breaking. Lake's whole reason to exist is that prompts and documents
    stay on the user's own machines, and losses L1 and L2 in the scope
    section are about data being seen or altered, not about anything
    crashing. If that guarantee fails quietly, the product is worse than
    the cloud service it replaces, because the user believes they are
    protected. The second is risk to the user's other work and property:
    Lake runs on computers that people use for other things, and a process
    that takes all the memory or the GPU can lose someone's unsaved work or
    make a machine unusable, which is loss L4. This kind of risk is easy to
    ignore because it does not show up in Lake's own tests, but it decides
    whether anyone lets Lake onto their machine at all. Both types also
    carry a reputational risk for the team: a tool that leaks data or
    crashes laptops is not one anyone recommends.
\end{enumerate}
