\section{Roadmap}
\label{SecRoadmap}

Every safety and security requirement in Section~\ref{SecSafetyReqs} is tied
to a hazard in the FMEA, and each is scheduled below against the project
milestones from the Development Plan. The order follows one rule: a
requirement is implemented in the same phase as the capability whose failure
it guards. Without that capability the hazard cannot occur, and with it the
hazard is live, so the guard cannot wait for a later phase. Requirements
that guard a capability outside the capstone scope are deferred, and the
reason is given.

The thresholds in these requirements (the memory safety margin in SR1-3,
the time-to-live in SR0-1, the timeouts in SR4-1, and the latency tolerance

on the team's own machines before each demonstration. The values and how
they are verified are recorded in the V\&V Plan.

\subsection{After the capstone}

The following are known hazards or mitigations that the capstone timeline
does not cover. Each is listed with the condition under which it would move
into scope.

\begin{itemize}
  \item \textbf{Encryption between nodes and device authentication.} The
    critical assumption in Section~\ref{SecAssumptions} is that the local
    network is private and trusted, which is also the Problem Statement's
    stretch goal. A potential user we interviewed for the SRS, who runs an
    on-premises assistant on export-controlled data, named encrypted
    traffic and company-managed machines as conditions for deploying
    anything like Lake. If the stretch goal is taken on, the assumption is
    removed and the hazards it currently excludes (an untrusted device on
    the network reading or injecting tensors) get FMEA rows and
    requirements of their own.
  \item \textbf{Backing off when a device owner is working.} Loss L4 covers
    a device that becomes unusable because of Lake. The current
    requirements limit memory use (SR1-3) but do not pause or throttle
    inference when the owner is active. The interviewee's first condition
    for pooling office machines was that Lake back off the moment the
    owner starts working. This becomes a requirement once Lake is run on
    machines that are not dedicated to it, which is after the capstone.
  \item \textbf{No telemetry, and auditability.} The same interview asked
    that Lake send nothing outside the cluster, including usage or crash
    reports, and that its behaviour be auditable. The SRS privacy
    requirement (NFR-G4-2-1) states that no request data leaves the cluster
    and that Lake sends no telemetry; it is verified by a network capture
    during a session. Auditability has no requirement yet and is deferred
    with the encryption and authentication work above, since it matters for
    the same organisational users.
\end{itemize}

\section{Appendix --- Reflection}

\input{../Reflection.text}

\begin{enumerate}
    \item What went well while writing this deliverable?
    \item What pain points did you experience during this deliverable, and how
    did you resolve them?
    \item Which of your listed risks had your team thought of before this
    deliverable, and which did you think of while doing this deliverable? For
    the latter ones (ones you thought of while doing the Hazard Analysis), how
    did they come about?
    \item Other than the risk of physical harm (some projects may not have any
    appreciable risks of this form), list at least 2 other types of risk in
    software products. Why are they important to consider?
\end{enumerate}
\noindent\rule{\linewidth}{0.4pt}

\begin{enumerate}
    \item Splitting the document by component worked. Matt had already
    named the five components for the SRS, so the system boundary section
    and the FMEA used the same names, and each hazard ID carries its
    component number (H1 for the partitioner, H3 for Tensor I/O). That made
    it easy to see which component had no hazards yet and go looking for
    them, and it means the safety requirements trace to the SRS without a
    separate mapping table. The losses table in the scope section also
    helped: once the four losses were written down, deciding whether
    something was a hazard became a matter of asking which loss it led to.

    \item The main pain point was that the Hazard Analysis and the SRS were
    written in the same two weeks by different people, and they depend on
    each other in both directions. The FMEA's recommended actions become
    the SRS safety requirements, but the FMEA also needed the SRS component
    list and the critical assumptions to exist first. We handled it by
    writing the SRS component section first and reusing its names and
    numbering here, and by opening one pull request per section so that a
    section could be reviewed as soon as it existed rather than waiting for
    the whole document. The second pain point was the FMEA table itself: a
    seven-column table that has to break across landscape pages is awkward
    in LaTeX. Ethan used an AI tool for the table formatting only, which is
    recorded in the disclosure.

    \item Two of the risks were on paper before this deliverable. The
    Development Plan's proof of concept section names network overhead
    making the split slower than a single device (H4-3), and the Problem
    Statement's dynamic allocation goal is built around devices dropping
    out of the pool mid-session (H2-1). A block larger than a device's
    memory (H1-3) was implicit in how the Development Plan describes the
    partitioner, but had not been written down as a failure. The rest came
    out of the FMEA. Walking the
    coordinator's responsibilities one at a time produced H0-1 and H0-2,
    stale health data and a missed partition notification, which we had
    not thought of because we had been picturing the happy path where every
    message arrives. The partitioner rows H1-1 and H1-2 came from asking
    what a correct partition even is, which forced us to write down that
    every layer is assigned exactly once and every node gets a non-empty
    block; that definition is now also the formalization in the SRS. The
    Tensor I/O rows H3-1 and H3-2 came from the question of what happens
    when a message arrives but is wrong rather than missing, which is a
    different failure from H4-1 and needs a different check. Finally, the
    user interview for the SRS, which happened during this deliverable,
    added two items to the roadmap that no one on the team had listed:
    backing off when a device owner is working, and sending no telemetry.

    \item Two other types of risk matter for Lake. The first is privacy and
    security risk: a software product can leak data without anything
    breaking. Lake's whole reason to exist is that prompts and documents
    stay on the user's own machines, and losses L1 and L2 in the scope
    section are about data being seen or altered, not about anything
    crashing. If that guarantee fails quietly, the product is worse than
    the cloud service it replaces, because the user believes they are
    protected. The second is risk to the user's other work and property:
    Lake runs on computers that people use for other things, and a process
    that takes all the memory or the GPU can lose someone's unsaved work or
    make a machine unusable, which is loss L4. This kind of risk is easy to
    ignore because it does not show up in Lake's own tests, but it decides
    whether anyone lets Lake onto their machine at all. Both types also
    carry a reputational risk for the team: a tool that leaks data or
    crashes laptops is not one anyone recommends.
\end{enumerate}
