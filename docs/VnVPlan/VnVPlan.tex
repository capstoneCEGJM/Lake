\subsubsection{Usability}

These tests cover NFR.S.1 (understandability), NFR.S.2 (controllability) and
NFR.S.3 (installability). The first is a session with people who have not used
\progname{}, which is the only way to check how a new user experiences the
interface. Its tasks and questions are in Section~\ref{sec:usability-survey}.

\begin{enumerate}

\item{T-NFR-USE-1\\}
\label{T-NFR-USE-1}

Type: Dynamic, manual

Initial State: Three devices run \progname{} on one local network. One device
has a background load that cuts its token throughput to about half, so it is
the bottleneck. \textit{DEMO\_MODEL} is on the device the participant uses.

Input/Condition: At least \textit{TEST\_USERS} participants who have not used
\progname{}, such as students from other capstone teams, each complete the two
tasks in Section~\ref{sec:usability-survey}.

Output/Result: Every participant completes task 1 (create a Lake network) and
task 2 (name the participating devices, the token throughput and the
bottleneck) within \textit{UI\_TASK\_TIME} each, and the throttled device is
highlighted as the bottleneck (FR.S.5.6). The answers to the follow-up
questions are recorded and each problem raised by more than one participant
becomes a GitHub issue.

How test will be performed: One team member runs the session and reads the
tasks aloud without giving hints. A second team member times each task from
the moment the participant first sees the interface and records whether it was
completed. The participant then answers the questions in
Section~\ref{sec:usability-survey}.

\item{T-NFR-USE-2\\}
\label{T-NFR-USE-2}

Type: Dynamic, manual

Initial State: A clean machine for each operating system with no previous
\progname{} installation, and the release installer or package for that
system.

Input/Condition: A team member installs \progname{} following only the
installation instructions.

Output/Result: On Windows and macOS, installation takes at most
\textit{INSTALL\_CLICKS} clicks after the installer is downloaded. On Linux it
takes one package manager command. On every system, \progname{} starts after
installation without further setup.

How test will be performed: The tester counts every click from opening the
installer to the first launch of \progname{}, and records the count and any
manual step needed. The test is repeated for each release candidate.

\end{enumerate}

\subsubsection{Performance}

These tests cover NFR.S.4 (model size), NFR.S.5 (scalability) and NFR.S.6
(intelligence). \hyperref[T-NFR-PERF-2]{T-NFR-PERF-2} measures how throughput changes with load, so
part of its output is a table and a graph rather than a single pass or fail.

\begin{enumerate}

\item{T-NFR-PERF-1\\}
\label{T-NFR-PERF-1}

Type: Dynamic, manual

Initial State: A Lake network of the team's laptops.
Let $M_{\max}$ be the largest free GPU-accessible memory of any
node and $M_{\mathrm{total}}$ the sum over all nodes, each reduced by
\textit{MEMORY\_MARGIN}. \textit{CAPACITY\_MODEL} is used at the lowest
precision whose memory need (weights plus the KV cache for
\textit{CONTEXT\_MAX} tokens) is greater than $M_{\max}$ and at most
$M_{\mathrm{total}}$.

Input/Condition: First, the model is loaded on the node with the most memory
alone. Then it is loaded across the whole Lake network and given the test
prompts.

Output/Result: Loading on one node fails with a partitioning failure
(FR.S.2.2). Loading across the network succeeds, and the responses meet the
criteria of the inference correctness tests in Section~\ref{sec:fr-tests}.

How test will be performed: The memory of each node is read from the
Coordinator's device report, and the precision is chosen from those values and
recorded with the result. The test is run once per demonstration with the
devices available at the time.

\item{T-NFR-PERF-2\\}
\label{T-NFR-PERF-2}

Type: Dynamic, automated

Initial State: Lake networks of $k = 1, 2, \ldots$ nodes, up to the number of
team devices available, running \textit{DEMO\_MODEL}.

Input/Condition: For each $k$, the number of concurrent requests $c$ is
increased through $1, 2, 4, 8, \ldots$ while each request generates
\textit{GEN\_TOKENS} tokens.

Output/Result: For each $k$, the largest $c$, called $c_{\max}(k)$, at which
the mean per-request token throughput is within \textit{MAX\_DEGRADATION} of the
single-request throughput. The test passes if $c_{\max}(k) \ge$
\textit{MIN\_CONCURRENT} for every $k \ge 2$ and $c_{\max}(k) \ge k \cdot
c_{\max}(1)$. The results are also reported as a table and a graph of
$c_{\max}$ against $k$.

How test will be performed: A load-test script sends the requests through the
OpenAI-compatible API and records the tokens per second of each request. The
results are kept for the Performance Report.

\item{T-NFR-PERF-3\\}
\label{T-NFR-PERF-3}

Type: Dynamic, automated

Initial State: \textit{DEMO\_MODEL} served two ways: by llama.cpp's
\texttt{llama-server} on one machine, and by a two-node Lake network.

Input/Condition: The same \textit{BENCH\_QUESTIONS} multiple-choice questions
from the MMLU benchmark, sent to both through the OpenAI-compatible API with
greedy decoding.

Output/Result: The Lake network's accuracy is at least \textit{BENCH\_RATIO} of
the single-machine accuracy. The relative error
$|a_{\mathrm{single}} - a_{\mathrm{Lake}}| / a_{\mathrm{single}}$ is reported, where
$a$ is the fraction of questions answered correctly.

How test will be performed: A script sends each question, extracts the answer
letter from the response, and scores both runs against the answer key. Using
\texttt{llama-server} as the baseline means both runs use the same API and
prompts, so only the split differs.

\end{enumerate}

\subsubsection{Look and Feel}

NFR.S.7 (consistency) is checked by inspection, since it concerns how the Lake
Client's source is written rather than how it behaves.

\begin{enumerate}

\item{T-NFR-LF-1\\}
\label{T-NFR-LF-1}

Type: Static, inspection

Initial State: The Lake Client source at a release candidate.

Input/Condition: Two team members who did not write the Lake Client code under
review go through this checklist:
\begin{enumerate}
  \item A search of the source for colour values (hexadecimal, \texttt{rgb()}
    and \texttt{hsl()}) and font names finds them only in the theme file.
  \item Every component takes its colours and fonts from the theme.
  \item Every screen of the Lake Client, viewed once, shows no colour or font
    outside the theme.
\end{enumerate}

Output/Result: All three items pass. Any failure is filed as a GitHub issue.

How test will be performed: The reviewers record the result of each item and
the commit reviewed in the pull request for the release candidate.

\end{enumerate}

\subsubsection{Fault Tolerance}

These tests cover NFR.S.8 (rejecting invalid model files) and NFR.S.9 (correct
results despite packet loss and corruption).

\begin{enumerate}

\item{T-NFR-FT-1\\}
\label{T-NFR-FT-1}

Type: Dynamic, automated

Initial State: A two-node Lake network on one machine, with no model loaded.

Input/Condition: Four invalid model files, each given to the Lake Client as the
model to load:
\begin{enumerate}
  \item \textit{SMALL\_MODEL} truncated to half its size;
  \item \textit{SMALL\_MODEL} with its first four bytes (the GGUF magic number)
    overwritten;
  \item a plain text file renamed with a \texttt{.gguf} extension;
  \item a valid GGUF file of a model architecture \progname{} does not support.
\end{enumerate}

Output/Result: Each file is rejected with an error message that names the
problem, no partition is sent to any node, and no process crashes.

How test will be performed: A test script loads each file in turn and checks
the error returned, the nodes' logs, and that every process is still running.

\item{T-NFR-FT-2\\}
\label{T-NFR-FT-2}

Type: Dynamic, automated

Initial State: A two-node Lake network on one Linux machine running
\textit{SMALL\_MODEL}, with the nodes connected through the loopback interface.

Input/Condition: The test prompts, run once with no network impairment and
then once for each packet loss rate and each packet corruption rate in
\textit{LOSS\_LEVELS}.

Output/Result: The generated tokens under every impairment are identical to the
tokens with no impairment. The time per token at each level is also recorded.

How test will be performed: The Linux \texttt{tc netem} tool adds the loss or
corruption to the loopback interface. The test runs in continuous integration
on a Linux runner.

\end{enumerate}

\subsubsection{Privacy}

These tests cover NFR.S.10 (no stored request data), NFR.S.11 (no data sent
outside the Lake network) and NFR.E.5 (no requests to third-party services).

\begin{enumerate}

\item{T-NFR-PRIV-1\\}
\label{T-NFR-PRIV-1}

Type: Dynamic, automated

Initial State: A two-node Lake network with \textit{SMALL\_MODEL} loaded and
logging at its most detailed level.

Input/Condition: The test prompts, each with a unique random marker string
added, sent through the API until every request completes.

Output/Result: A search of every file \progname{} wrote on every node, including
its data directory, logs and temporary files, finds none of the marker strings
and none of the response text.

How test will be performed: A script records the files \progname{} creates or
changes during the run and searches them for each marker and response.

\item{T-NFR-PRIV-2\\}
\label{T-NFR-PRIV-2}

Type: Dynamic, manual

Initial State: A two-node Lake network on a local network, with packet capture
running on every node.

Input/Condition: A session of \textit{IDLE\_TIME} with no requests, then the
test prompts, then shutting the Lake network down.

Output/Result: Every captured packet sent by \progname{} goes to another node of
the Lake network, to a device on the local network being discovered or invited,
or to the client that sent the request. There are no other destinations,
including no name lookups for outside hosts.

How test will be performed: A team member captures traffic with
\texttt{tcpdump} on Linux and macOS or Wireshark on Windows, filters it to the
\progname{} processes, and lists every destination address and port.

\end{enumerate}
