\tocsection{Glossary}
\label{sec:glossary}

\begin{itemize}
    \item \textbf{Activation} -- An intermediate value that is computed during the text generation of an LLM.
    \item \textbf{Device pool} -- A collection of nodes that comprise the Lake network.
    \item \textbf{FFI (Foreign Function Interface)} -- An interface that allows code written in different languages to call one another.
    \item \textbf{FLOP/s (Floating-point Operations per Second)} -- The number of floating point arithmetic operations performed per second. Used as a measure of computational performance.
    \item \textbf{Inference} -- The process of using an LLM to generate text.
    \item \textbf{Inference Engine} -- The software module that loads the LLM and executes its model layer partitions to generate output.
    \item \textbf{KV cache} -- The cache of key-value pairs that are used to store the activations of an LLM.
    \item \textbf{Lake} -- A decentralized network of devices that work together to serve LLM inference via model layer partitioning.
    \item \textbf{Lake Client} -- The user-facing client interfaces for both consuming the API responses and configuring the Lake system.
    \item \textbf{Latency} -- The elapsed time between the start of an inference request and a defined event, such as the completion of the first token, or the completion of the entire response.  
    \item \textbf{LLM (large language model)} -- An artificial intelligence model that is trained on a large dataset of text and is used to generate text.
    \item \textbf{Model layer partitioning} -- The distribution of an LLM's layers across a device pool.
    \item \textbf{Node} -- A participating device within the Lake network.
    \item \textbf{Quantization} -- The process of converting an LLM's weights to a lower precision format to reduce memory usage.
    \item \textbf{Session} -- A unit of interaction between a user and Lake to serve one or more inference requests.
    \item \textbf{Token} -- A unit of text that is processed by an LLM, typically a word or a subword.
    \item \textbf{Token throughput} -- The number of tokens that can be generated by an LLM per unit time.
    \item \textbf{Weights} -- The parameters of an LLM that determine its behavior when generating text. 


\end{itemize}

This following explains why Lake exists and what it is for, in terms a reader
outside the team can follow. How the system is built is left to the System
chapter (Section~\ref{sec:srs-S}), and the world it runs in to the Environment
chapter (Section~\ref{sec:srs-E}).

\subsection{Context and Overall Objective}\label{subsec:context-and-overall-objective}

LLMs have become an everyday tool, and almost everyone
who uses one does so through a commercial provider's web interface or
application programming interface (API). The alternative is to run an open
model on your own machine, which keeps your data at home but limits you to
whatever fits in one device's memory. Most households, offices, and labs
already own several computers, and most of them sit idle most of the time.

Lake runs a single pre-trained LLM across several consumer devices on one
local network. The model is split by layer, each device holds and runs only
its share, and the devices pass intermediate results between them so that
together they answer a prompt as if the model were running on one machine.
The objective is to let people run models that are too large for any one of
their devices, privately and on hardware they already own, and to keep the
model running as devices join and leave the network.

Figure~\ref{fig:context-diagram} shows where Lake's boundary sits. Lake is the
software on each participating device. The devices themselves, the network
between them, the model file, and the tools a user sends prompts from are all
outside the boundary.

\subsection{Current Situation}\label{subsec:current-situation}

Today there are two ways to use an LLM. The first is a hosted service from one
of the major inference providers. These give the best model quality, but every
prompt leaves the premises, the cost grows with use, and the user has no
control over how their data is handled. For a clinic or a law office this is
often not acceptable at all.

The second is local inference with a tool such as llama.cpp
\citep{LlamaCpp} or Ollama \citep{Ollama}. The model runs in one process on
one machine, so the largest model a user can run is set by the memory of their
single best device. A laptop that runs a small model well may run a mid-sized
one slowly and a large one not at all, even when three other computers sit on
the same desk.

A few projects already spread a model over several machines: exo
\citep{Exo}, prima.cpp \citep{PrimaCpp2025}, and the remote procedure call
(RPC) backend of llama.cpp. They assign layers to devices once, when the model
loads, and the assignment stays fixed for the session. If a device drops off
the network the session fails, and a device added later goes unused until
everything is restarted. Lake builds on the same idea but makes the assignment
something the system can change while it is running.
Table~\ref{tab:alternatives} summarises how Lake compares. Mixed operating
systems are marked ``partly'' for the existing tools because exo runs on
Apple silicon through MLX and only on the CPU on Linux, with no Windows build
\citep{Exo}, and prima.cpp supports Linux and macOS \citep{PrimaCpp2025};
only the llama.cpp RPC backend runs on all three.

\subsection{Expected Benefits}\label{subsec:expected-benefits}

The benefits below follow the goals in the Problem Statement: the four
numbered goals and concurrent inference, which is a goal in its own right
because serving several requests at once is one of the main advantages of
splitting a model by layers.
Figure~\ref{fig:goal-model} is a goal model thats reflects this. Each benefit below states the measure we
will use to check it, and the requirements that deliver them are in
Section~\ref{subsec:functionality}.

\begin{landscape}
\begin{figure}[p]
    \centering
    \includegraphics[width=\linewidth]{goal_model.png}
    \caption[Goal model]{Goal model for Lake and its stakeholders.}
    \label{fig:goal-model}
\end{figure}
\end{landscape}

\subsubsection*{Larger models on existing hardware}
A user can run a model that does not fit on any one of their devices. The
measure is the largest model, by parameter count, precision, and context
window, that a cluster can serve compared with the largest the single best
device in that cluster can serve alone. This is the primary benefit, and the
Model Size requirement in Section~\ref{subsec:functionality} states the
target.

\subsubsection*{Privacy}
Prompts, responses, and the model's intermediate data stay on the devices in
the cluster and never go to an external provider. The measure is that no
request data leaves the cluster during a session. What privacy does and does
not cover in the first release is stated in
Section~\ref{subsec:limitations-and-exclusions}.

\subsubsection*{Lower cost}
There are no per-token or subscription fees, and no new hardware is needed
beyond what the user already owns. The measure is that a cluster can be formed
entirely from machines the user had before installing Lake.

\subsubsection*{Resilience to devices coming and going}
When a device leaves or joins, Lake reassigns layers and keeps serving
requests as long as the remaining cluster has enough memory. The measures are
whether requests are served after a reassignment and how long the
reassignment takes, which Section~\ref{subsec:formalizations} defines
precisely.

\subsubsection*{Mixed platforms in one cluster}
Windows, macOS, and Linux machines can be combined, so a user is not limited
to devices of one type. The measure is a working cluster that mixes all three.

\subsubsection*{Works with the tools people already use}
Lake exposes the same API format as the major hosted providers, so existing
chat interfaces and coding assistants can point at Lake instead of a cloud
service with no changes on their side. The measure is an unmodified
third-party client completing a session against Lake.

\subsubsection*{Several users at once}
While one request's token is being computed on one node, another request's
token can be computed on the next, so a cluster can serve several users
without each one waiting for the others. The measure is the number of
requests the cluster can serve at once before any single request slows by
more than the tolerance set in the Scalability requirement in
Section~\ref{subsec:functionality}, and how that number grows with the
number of nodes.

\subsubsection*{Speed, where the split allows it}
Response time and throughput (tokens per second) for a single request are
secondary measures. A split model is not expected to beat a single device
on a model that already fits on that device, since every token still passes
through every layer in order. The gain is in capacity, and in throughput
when several requests are served at once. The practitioner we interviewed (see
Section~\ref{subsubsec:g7-sources}) expected the same: a split over an office
network would likely be slower than one good GPU for live chat, but worth it
for background work such as re-indexing documents, OCR, and overnight test
runs, which is a use we had not considered.

\subsection{Functionality Overview}\label{subsec:functionality-overview}

This section is a capsule version of the System chapter. Each high-level
requirement here maps to one or more of the components in

\subsubsection{Functional Requirements}\label{subsubsec:g4-functional}

These are the high-level requirements, stated for the reader of the Goals
chapter. Each ends with the detailed, verifiable requirements in
Section~\ref{subsec:functionality} and the Environmental Requirements table
that realise it, so a change in either place can be traced to the other.

\begin{itemize}
    \item \label{FR.G.4.1}\textbf{FR.G.4.1 Form a cluster with consent.}
    Lake runs on each device. From the web user interface (UI) on one device,
    which becomes the leader node, the operator sees the other devices on the
    local network that are running Lake and chooses which to include. Each
    chosen device asks its owner to confirm before it joins, so no device
    takes part without consent. \emph{Realised by} FR.S.1.4, FR.S.5.1, FR.S.5.2, FR.S.1.17, FR.S.1.18, FR.S.1.20, FR.S.1.21, FR.S.5.7, and NFR.S.12.
    \item \label{FR.G.4.2}\textbf{FR.G.4.2 Load and partition a model.}
    The operator picks a model in GGUF format \citep{GGUF}, the file format
    used by llama.cpp. Lake measures each node's memory, compute, and network
    performance, decides which range of layers each node will hold, and has
    each node load only that range. \emph{Realised by} FR.S.5.3, FR.S.1.8, FR.S.2.1 to FR.S.2.4, FR.S.1.6, FR.S.1.19, and FR.S.3.1.
    \item \label{FR.G.4.3}\textbf{FR.G.4.3 Run inference across the
    cluster.} A prompt enters at the first node, the activations pass from
    node to node in layer order, and generated tokens stream back to the user
    one at a time. Each node keeps the key-value (KV) cache for its own
    layers, so nothing about the conversation has to be re-sent between
    tokens. Several requests can be in flight at once, each at a different
    node, and their state is kept apart. \emph{Realised by} FR.S.3.2, FR.S.3.3, FR.S.4.1, FR.S.4.3, FR.S.4.4, and, for concurrent requests, FR.S.1.14, FR.S.3.5, FR.S.4.6, and NFR.S.5.
    \item \label{FR.G.4.4}\textbf{FR.G.4.4 Reallocate when the cluster
    changes.} When a node leaves, fails, or joins, the leader re-partitions
    the model across the nodes that remain and resumes serving, retrying any
    request that was in progress. If the cluster no longer has enough memory
    for the model, the user is told why rather than left with a hung session. \emph{Realised by} FR.S.1.10 to FR.S.1.13, FR.S.1.22, FR.S.2.2, and FR.S.5.4.
    \item \label{FR.G.4.5}\textbf{FR.G.4.5 Measure performance.} Lake
    records compute time on each node and transfer time between nodes. These
    measurements drive the partitioner and are shown in the web UI, which
    highlights the node or link that is the bottleneck and compares the
    cluster against the single best machine in it, so the operator can see
    whether pooling is paying off. \emph{Realised by} FR.S.1.2, FR.S.1.3, FR.S.1.7, FR.S.1.23, FR.S.3.4, FR.S.4.5, FR.S.5.5, FR.S.5.6, and NFR.S.1.
    \item \label{FR.G.4.6}\textbf{FR.G.4.6 Serve prompts through a standard
    API.} The leader node exposes an HTTP API in the OpenAI format
    \citep{OpenAIAPI}, including streaming and tool calling, so any client
    that can talk to a hosted provider can talk to Lake. \emph{Realised by} FR.S.1.9 and NFR.E.3.
\end{itemize}

Two of these carry most of the value: \hyperref[FR.G.4.2]{FR.G.4.2}
and \hyperref[FR.G.4.4]{FR.G.4.4}.
Partitioning is what lets a model larger than any one device run at all,
which is the primary goal of the project. Reallocation is what sets Lake
apart from exo and the llama.cpp RPC backend, both of which fix the split
when the model loads. Without the first there is no product; without the
second there is nothing a user could not already get elsewhere.

\subsubsection{Non-Functional Requirements}\label{subsubsec:g4-nonfunctional}

These state how well Lake must do what Section~\ref{subsubsec:g4-functional}
describes. Each is a quality the system must have, not a design choice, and
each names the detailed requirement that gives it a measurable target.

\begin{itemize}
    \item \label{NFR.G.4.1}\textbf{NFR.G.4.1 Request data stays in the
    cluster.} No prompt, response, or intermediate data is sent to any device
    outside the cluster, none is kept after a request completes, and Lake
    sends no telemetry. This is the privacy benefit, and it is the reason an
    organisation handling export-controlled or medical data could use Lake at
    all. \emph{Realised by} NFR.S.10, NFR.S.11, NFR.S.12, and NFR.E.5.
    \item \label{NFR.G.4.2}\textbf{NFR.G.4.2 Runs on Windows, macOS, and
    Linux.} Each is a supported platform for any node, and one cluster can
    mix all three. This is the cross-platform goal from the Problem
    Statement. \emph{Realised by} NFR.S.3, NFR.S.13 to NFR.S.15, and NFR.E.1.
    \item \label{NFR.G.4.3}\textbf{NFR.G.4.3 The split does not change the
    model.} A model run through Lake produces output of the same quality as
    the same model run on one machine, within the tolerance set by NFR.S.6.
    Users
    would not trust a system that made their model worse. \emph{Realised by} NFR.S.6, FR.S.2.3, and NFR.E.4.
    \item \label{NFR.G.4.4}\textbf{NFR.G.4.4 License compliance.} Lake
    respects the licenses of the software it builds on and of the models it
    runs, as set out in Section~\ref{subsec:standards}. \emph{Realised by} NFR.E.7 and NFR.E.8.
    \item \label{NFR.G.4.5}\textbf{NFR.G.4.5 Installable without expert
    help.} A user can install Lake on each supported platform from an
    installer or a single package-manager command, without building from
    source or editing configuration files. Both the home user and the
    organisation in Section~\ref{subsec:user-profiles} said they would not
    deploy a tool that needs more than that. \emph{Realised by} NFR.S.3.
    \item \label{NFR.G.4.6}\textbf{NFR.G.4.6 Serves more users as nodes
    are added.} The number of requests a cluster can serve at once without
    any one of them slowing beyond a set tolerance grows with the number of
    nodes. This is the measure behind the concurrent inference goal.
    \emph{Realised by} NFR.S.5.
\end{itemize}

Privacy and fidelity matter most. A local inference tool that leaked data or
degraded the model would fail the two groups it is meant for: the
privacy-bound organisation and the user who already has a model they like.

        \item The operator selects the computers to include.
        \item Each selected computer's owner confirms (\hyperref[UC2]{UC2}).
        \item The cluster is shown with each computer's memory and platform.
    \end{itemize}

    \item \label{UC2}\textbf{UC2 Confirm a device joining}
    \begin{itemize}
        \item A prompt appears on the device asking whether it may join the
        named cluster.
        \item The owner accepts or declines.
        \item If accepted, the device joins and the owner can see what it is
        doing; if declined, it is left out.
    \end{itemize}

    \item \label{UC3}\textbf{UC3 Run a model across the cluster}
    \begin{itemize}
        \item The operator chooses a model file, which may be larger than any
        one computer can hold.
        \item Lake reports that the model is loaded across the cluster.
        \item A user sends a prompt.
        \item The response streams back word by word.
        \item The user sends further prompts in the same session.
    \end{itemize}

    \item \label{UC4}\textbf{UC4 Use Lake from an existing tool}
    \begin{itemize}
        \item A user opens the chat interface or coding assistant they
        already use.
        \item They point it at Lake's address instead of a cloud provider.
        \item They use the tool as before; prompts and responses go through
        Lake and stay on the local network.
    \end{itemize}

    \item \label{UC5}\textbf{UC5 Keep working when a device leaves}
    \begin{itemize}
        \item During a session, a computer in the cluster is closed or
        disconnected by its owner.
        \item Lake tells the operator which device left and that it is
        reorganising.
        \item The user's current prompt is answered, or re-run, without being
        resubmitted. A partial answer is never presented as a complete one.
        \item If the remaining computers cannot hold the model, the operator
        is told why and what would fix it.
    \end{itemize}

    \item \label{UC6}\textbf{UC6 Add a device during a session}
    \begin{itemize}
        \item The operator selects a new computer that has appeared on the
        network.
        \item Its owner confirms (\hyperref[UC2]{UC2}).
        \item Lake reorganises to use the new computer and shows the new
        arrangement.
        \item The user continues prompting and sees the change in speed.
    \end{itemize}

    \item \label{UC7}\textbf{UC7 Find the bottleneck}
    \begin{itemize}
        \item Responses feel slow, so the operator opens the cluster view.
        \item The view shows how long each computer and each connection takes
        per word generated, and marks the slowest.
        \item The operator decides whether to swap a cable, remove a
        computer, or add one.
    \end{itemize}

    \item \label{UC8}\textbf{UC8 Serve several users at once}
    \begin{itemize}
        \item Two or more users send prompts to the same cluster at the same
        time, from their own tools.
        \item Each sees their own response stream back, and none sees
        another's prompt or answer.
        \item Each response arrives about as fast as it would have alone,
        until the cluster is busy enough that the operator sees requests
        queue in the cluster view.
    \end{itemize}
\end{enumerate}

\subsection{Limitations and Exclusions}\label{subsec:limitations-and-exclusions}

Lake is deliberately narrow. The following are out of scope. The stretch
goals from the Problem Statement are listed as exclusions until the team
decides to take them on. The likely and unlikely changes listed at the end of
the System chapter record which of these may change.

\begin{itemize}
    \item \emph{No training or fine-tuning.} Lake runs pre-trained
    transformer models that ggml \citep{Ggml} supports. Lake does not train,
    fine-tune, quantize, or otherwise modify a model, and does not change the
    quality of its output.
    \item \emph{Trusted network and devices.} In the first release, traffic
    between nodes is not encrypted and devices are not authenticated beyond
    the owner's confirmation. Privacy therefore means that data never leaves
    the user's own network, not that it is protected from other devices on
    that network. Users must run Lake only on devices they trust and a
    network they control. Encryption and authentication are a stretch goal.
    \item \emph{Supported hardware.} Each device needs a GPU from Nvidia,
    AMD, or Apple, because inference on a CPU alone is too slow to be useful
    in a cluster. Smartphones are a stretch goal.
    \item \emph{Wired connections first.} The first revision targets wired
    Ethernet. Wireless operation is a stretch goal because its latency and
    variability may make the split model too slow.
    \item \emph{Not faster for models that already fit.} Lake does not speed
    up a model that already runs well on one device. The benefit is running
    models that would not otherwise fit.
    \item \emph{No model hosting.} Lake does not download or distribute
    model weights. Users supply a model file under that model's own license.
\end{itemize}

\paragraph{Course material and the template.} The course templates, rubrics,
and lectures, and Meyer's handbook \citep{Meyer2022}, which this document's

\subsection{Environment Components}\label{subsec:environment-components}

\begin{itemize}
    \item \textbf{Inference users (a.k.a users)} -- Individuals who interact with the Lake network to serve inference requests.
    \item \textbf{Lake operators} -- Individuals who manage the Lake network, including the device pool and the model.
    \item \textbf{Device owners} -- Individuals who contribute one or more nodes towards the device pool.
    \item \textbf{Operating systems and drivers} -- Windows, macOS, and Linux operating systems that have the supported drivers to facilitate inference requests. Android and iOS operating system support is a stretch goal.
    \item \textbf{Network equipment} -- Routers, switches, Thunderbolt cables, and any other hardware necessary to connect the nodes to the network. Connectivity via Wi-Fi is a stretch goal.
    \item \textbf{Model} -- Pre-trained and open-source model weights that are permitted to be downloaded and utilized by the Lake network via model layer partitioning.
    \item \textbf{External API consumers} -- Other services that utilize the Lake API to serve inference requests. This acts as the main interface for consumers to use Lake, such as coding agent harnesses (e.g. Claude Code, Codex, Pi).
 
\end{itemize}

\subsection{Constraints}\label{subsec:constraints}

\begin{itemize}
    \item \textbf{Device hardware} -- Each node should have a sufficient CPU, GPU, memory, and storage such that its assigned model layers, KV cache, and other Lake software components can fit and run within the device, such that distributed inference has both a higher token throughput and lower latency than an equivalent single-device inference.
    \item \textbf{Network communication} -- Network communication, whether wired or wireless, should have a sufficiently high bandwidth and low latency. Inter-node communication overhead may make distributed inference slower than single-device inference.
    \item \textbf{Platform compatibility} -- Nodes within the Lake network must operate on Windows, macOS, and Linux (as well as Android and iOS as stretch goals) as hardware acceleration and inference platforms are limited by the available drivers on these operating systems.
    \item \textbf{API compatibility} -- Lake must implement a standardized OpenAI API spec such that existing external clients can easily utilize Lake, \citep{OpenAIAPI}, as specified in Section S.3.
    \item \textbf{Model architecture} -- Only supported LLM architectures that Lake's model layer partitioning supports can be used.
\end{itemize}

\subsection{Assumptions}\label{subsec:assumptions}

\begin{itemize}
    \item \textbf{Device owners authorize their nodes for use} -- Device owners have authorized their device to be used in the Lake network as a node for serving inference.
    \item \textbf{Participating nodes are trusted devices within the Lake network} -- Each node is trusted to run and process potentially sensitive inference data.
    \item \textbf{Permitted model use} -- Lake operators are using permitted models for inference that adhere to the respective licensing.
    \item \textbf{Network reachability} -- Nodes within the Lake network must be able to communicate over a network connection.
    \item \textbf{Model suitability} -- Models that are suited for a given task are used when Lake is serving inference (e.g. a larger model for logic/coding-based tasks, a smaller model for conversational tasks).
    \item \textbf{Trusted local network} -- The local network connecting the participating nodes is private and trusted by the operator.
\end{itemize}

\subsection{Effects}\label{subsec:effects}

\begin{itemize}
    \item \textbf{Resource usage} -- Device owners' CPU/GPU, memory, and disk usage will increase while the device is part of the Lake network, potentially making the device too resource constrained to multi-task or perform other activities. When not in use, any cached data or the stored layers can continue to utilize disk space.
    \item \textbf{Energy usage} -- Devices will consume more power, increasing energy usage, heat generated, fan usage, and decreasing battery life if unplugged.
    \item \textbf{Network bandwidth usage} -- The Lake network may utilize a large amount of a network's bandwidth, inhibiting other devices or processes from accessing the network.
    \item \textbf{Logged data} -- During inference, logs and other diagnostic information can be stored and persist on the node's disk. Logs must exclude sensitive request data as specified in SR5-2.
    \item \textbf{Access to inference} -- Users can gain access to inference that they previously would not be able to get within a single device or with a paid service.
\end{itemize}

\subsection{Invariants}\label{subsec:invariants}

\begin{itemize}
    \item The provided model must remain unchanged. Loading the model and partitioning its layers must not mutate the underlying model weights.
    \item Inference must be contained within the Lake network, and must not be sent to 3rd-party services.
    \item All nodes within the Lake network must be using compatible layer partitions that originate from the same model's layers.
    \item All nodes must serve inference in a way that the activations are performed in the same order as in single-device inference.
    \item Intermediate data from one request must not be used for another independent request.
\end{itemize}

\subsection{Standards and Legal/Regulatory Factors}\label{subsec:standards}

\noindent\textbf{Standards:}
\begin{itemize}
    \item \textbf{API compatibility} -- Lake's inference API will follow the OpenAI API endpoints for requests and response formats, as specified in S.3.
    \item \textbf{Coding conventions} -- Black code style and Ruff lint checks will be used for Python components \citep{Black,Ruff}. Rustfmt and Clippy will be used for Rust components \citep{Rustfmt,Clippy}. Prettier and ESLint will be used for TypeScript components \citep{Prettier,ESLint}.
\end{itemize}

\noindent\textbf{Legal and Regulatory Factors:}
\begin{itemize}
    \item \textbf{Software licensing} -- Lake is available under the GNU GPL v3.0 license \citep{GPU2007}. All dependencies used in Lake must be compliant and compatible with Lake's intended use and distribution.
    \item \textbf{Model licensing} -- Pretrained LLMs used for inference are subject to their respective licenses. Lake must be compliant with these licenses for its use and distribution.
\end{itemize}

\subsection{Components}\label{subsec:components}
\begin{figure}[H]
    \centering
	\adjustbox{center}{\includegraphics[width=1.4\textwidth]{component_diagram.png}}
    \caption{Component diagram.}
    \label{fig:component-diagram}
\end{figure}

\begin{itemize}
	\item \textbf{Coordinator} -- This component exists on all nodes,
		but the following responsibilities are only run on the leader node:
		\begin{itemize}
			\item Providing an OpenAI-API compatible API to the user for use with tools like
				\href{https://opencode.ai/}{OpenCode}.
			\item Tracking cluster health, and detecting node failures.
			\item Notifying nodes of partitioning changes.
			\item Rebuilding the cluster and saving in-progress requests
				in the case of node failure, removal, or addition.
			\item Measuring node connection performance.
		\end{itemize}
		On a follower node, it is primarily responsible for managing the inference engine
		on its device, following the instructions of the leader node.

	\item \textbf{Model Partitioner} --
		This component determines how to partition the model among the participating devices. It
		decides at which points to cut the graph, how large each partition is, and which device gets
		each partition. This component is integral to ensuring that each device is assigned an appropriate
		partition given the device's computational and networking performance.

	\item \textbf{Inference Engine} --
		This component is the high-performance inference engine running on each device. It will handle
		execution of the given model partition for each device. It will call into
		\href{https://github.com/ggml-org/ggml}{ggml} using the Rust-to-C FFI to control the execution of a
		device's model partition.

	\item \textbf{Tensor I/O} --
		This component handles the compressing, sending, receiving, and decompressing of tensors between devices.
		It will leverage \href{https://grpc.io/}{gRPC} for high-performance communication, with the potential
		to use a custom solution should \href{https://grpc.io/}{gRPC} fail to meet our requirements in practice.

	\item \textbf{Web UI} --
		This component handles displaying cluster information and structure to the user, as well as allowing user
		inputs to configure a new cluster, or modify an existing cluster.
\end{itemize}

			\item \label{FR.S.1.16}\textbf{FR.S.1.16} The system shall provide the Web UI with cluster information, and
				accept cluster configuration instructions from the Web UI.
			\item \label{FR.S.1.17}\textbf{FR.S.1.17} The system shall not begin inference until all selected followers have
				confirmed participation. Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.18}\textbf{FR.S.1.18} The system shall only include selected followers in a new cluster.
				Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
		\end{itemize}
	\item \textbf{When running on a follower node:}
		\begin{itemize}
			\item \label{FR.S.1.19}\textbf{FR.S.1.19} The system shall accept model partition assignments from the
				leader node Coordinator.
			\item \label{FR.S.1.20}\textbf{FR.S.1.20} The system shall, upon receiving an invite to join a cluster,
				request that the user confirm or decline participation. Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.21}\textbf{FR.S.1.21} The system shall not partake in a cluster without user confirmation.
				Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.22}\textbf{FR.S.1.22} The system shall not require confirmation to re-join a rebuilding cluster
				led by the same device, so long as the local device was already participating in the original cluster.
			\item \label{FR.S.1.23}\textbf{FR.S.1.23} The system shall report collected health/performance data to the
				leader node Coordinator on a 5 second interval.
				Partially satisfies hazards H0-1 and H0-2 from the Hazard Analysis.
			\item \label{FR.S.1.24}\textbf{FR.S.1.24} The system shall assume the leader node has failed if there has been
				no health query from the leader node for more than 60 consecutive seconds.
			\item \label{FR.S.1.25}\textbf{FR.S.1.25} The system shall initiate the shutdown of the local node, if the leader
				node is assumed to have failed. Partially satisfies hazards H4-2 and H4-1 from the Hazard Analysis.
				\begin{quote}
					\textbf{Rationale:} The Leader node is the device the user is physically using to interact with the cluster,
					so failure of that device will remove the user's ability to use the cluster, whether or not the cluster survives.
					The architecture of Lake will allow the ability to recover from a leader failure to be implemented at a later date.
				\end{quote}
		\end{itemize}
\end{itemize}

\subsubsection{Model Partitioner}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.2.1}\textbf{FR.S.2.1} The system shall assign all devices a partition smaller than their available
		GPU-accessible memory, with additional room left for runtime overhead. Related to \hyperref[NFR.S.4]{NFR.S.4}.
		Satisfies hazard H1-3 from the Hazard Analysis.
	\item \label{FR.S.2.2}\textbf{FR.S.2.2} The system shall report failure in the case that no valid partition across
		the cluster exists (e.g. not enough GPU-accessible memory).
	\item \label{FR.S.2.3}\textbf{FR.S.2.3} The system shall produce partitions that when assembled, are equivalent
		to the original model. Satisfies \hyperref[NFR.S.6]{NFR.S.6}.
	\item \label{FR.S.2.4}\textbf{FR.S.2.4} The system shall assign larger partitions to more capable
		devices\footnote{The "capabilities" of any given devices are defined via a combination of network throughput,
		GPU TFLOPs/TOPs, GPU-accessible memory size, and GPU-accessible memory bandwidth (GB/s).}.
		Related to \hyperref[NFR.S.4]{NFR.S.4}.
\end{itemize}

\subsubsection{Inference Engine}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.3.1}\textbf{FR.S.3.1} The system shall load the model partition given by the local Coordinator into
		GPU-accessible memory.
	\item \label{FR.S.3.2}\textbf{FR.S.3.2} The system shall accept incoming tensors from Tensor I/O, and run them
		through the loaded partition.
	\item \label{FR.S.3.3}\textbf{FR.S.3.3} The system shall send output tensors to Tensor I/O.
	\item \label{FR.S.3.4}\textbf{FR.S.3.4} The system shall measure partition performance
		metrics\footnote{e.g. token throughput, end-to-end partition latency, backpressure.} and provide them to the local
		Coordinator on a 5 second interval.
	\item \label{FR.S.3.5}\textbf{FR.S.3.5} The system shall support processing tensors from multiple different
		requests concurrently. Related to \hyperref[NFR.S.5]{NFR.S.5}.
\end{itemize}

\subsubsection{Tensor I/O}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.4.1}\textbf{FR.S.4.1} The system shall establish connections with neighbouring nodes' Tensor I/O components.
	\item \label{FR.S.4.2}\textbf{FR.S.4.2} The system shall dynamically choose the compression level of
		outgoing tensors to maximize throughput based on available CPU-time and network throughput.
	\item \label{FR.S.4.3}\textbf{FR.S.4.3} The system shall accept input tensors from the upstream node, decompress them,
		and provide them to the Inference Engine.
	\item \label{FR.S.4.4}\textbf{FR.S.4.4} The system shall accept output tensors from the Inference Engine, compress
		them, and send them to the downstream node's Tensor I/O.
	\item \label{FR.S.4.5}\textbf{FR.S.4.5} The system shall measure network performance
		data\footnote{e.g. RTT, throughput, backpressure.}, for established connections, and provide
		that data to the local Coordinator on a 5 second interval.
	\item \label{FR.S.4.6}\textbf{FR.S.4.6} The system shall maintain request association when sending
		tensors\footnote{This is to allow tensors from different concurrent requests to be differentiated.}.
		Related to \hyperref[NFR.S.5]{NFR.S.5}.
\end{itemize}

\subsection{Interfaces}\label{subsec:interfaces}
Lake requires the following interfaces:
\begin{itemize}
    \item \textbf{OpenAI compatible API} -- An HTTP server, following the OpenAI API structure.
		This will be the API used to interact with the user, via third-party tools of the user's
		choice that accept the OpenAI API (e.g. \href{https://opencode.ai/}{OpenCode}).
	\item \textbf{GGUF input model} -- An input file using the
		\href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF} file format. This contains
		the model Lake will partition and run.
	\item \textbf{Rust-to-C FFI} -- The Rust-to-C foreign function interface will be used to call
		\href{https://github.com/ggml-org/ggml}{ggml} from the Inference Engine.
	\item \textbf{gRPC between nodes} -- A gRPC-based API used to communicate between nodes.
	\item \textbf{REST API between Coordinator and Web UI} -- A REST API for communication between the
		leader Coordinator and the Web UI.
\end{itemize}

\subsection{Normal Operation}\label{subsec:normal-operation}
\begin{enumerate}
	\item User opens Lake client instances on all participating machines.
    \item User creates a Lake cluster using the UI on one of the devices, and provides a
		\href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF} file. This
		device becomes the leader node.
	\item Leader node checks connectivity with follower nodes, and collects performance
		metrics for each node.
	\item Partitioner devises a partitioning scheme based on the collected metrics.
	\item Leader node sends the model partitions to their respective devices.
	\item Neighbouring nodes on the partition graph establish direct P2P connections.
	\item User initiates inference request by providing a prompt via the OpenAI compatible
		API.
	\item Leader node sends the prompt tokens to the inference engine corresponding to the
		first node of the graph, initiating prefill.
	\item Prompt tokens propagate through the graph until prefill completes, and the first
		output token is generated.
	\item Output tokens are repeatedly fed back into the top of the graph, generating a new token
		on each iteration until the response is complete.
	\item As the response generates, the user receives the generated output via the OpenAI compatible
		API.
	\item User initiates a shutdown of the Lake cluster.
	\item Each node unloads its portion of the graph.
	\item Leader node saves the cluster configuration to disk.
	\item All nodes sever their connections, and all Lake client instances terminate.
\end{enumerate}

\subsection{Undesired Event Handling}\label{subsec:undesired-event-handling}
\begin{itemize}
    \item \textbf{Model is too large for the available memory in the cluster} --
		The Partitioner reports a partitioning failure, and this error is communicated to the
		user via the Web UI.
	\item \textbf{Follower node fails during inference} -- Leader node re-tries inference,
		if it continues to fail, the leader rebuilds the cluster, excluding the problematic device.
		Associated with hazard H2-1 in the Hazard Analysis.
	\item \textbf{Tensors are corrupted on transfer between nodes} -- The receiving Tensor I/O
		requests that the tensor is retransmitted from the source Tensor I/O.
		Associated with hazard H3-1 in the Hazard Analysis.
	\item \textbf{Connection between two nodes is lost} -- The nodes in question attempt to
		re-establish a connection. If this fails, the leader must rebuild the cluster, excluding
		the failed link. Associated with hazard H4-1 in the Hazard Analysis.
	\item \textbf{Input \href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF}
		file is corrupted or fails to load} --
		Refuse to begin inference, and inform the user of the corrupted or faulty file.
	\item \textbf{A request is made with a larger prompt than the cluster has memory for} --
		If there are existing requests running, wait for them to complete, then try again.
		If there is still not enough memory, return an error for the request, and instruct the user
		to shorten their prompt or context window.
	\item \textbf{A rebuilt cluster is too small to hold the model after a node leaves} --
		The Partitioner reports a partitioning failure, and this error is communicated to the
		user via the Web UI.
	\item \textbf{A user attempts to create a cluster with a node without a GPU} --
		The Web UI displays an error message outlining the requirement for all nodes to have a GPU.
\end{itemize}

\subsection{Detailed Usage Scenarios}\label{subsec:detailed-usage-scenarios}

This section expands each high-level scenario from
Section~\ref{subsec:high-level-usage-scenarios} (UC1--UC8) into a full use
case with preconditions, guarantees, a numbered main success scenario, and
extensions. Step numbers in the extensions refer to the main success
scenario of the same use case.

% ---------------------------------------------------------------------------
\subsubsection*{UC1: Form a cluster}\label{sec:uc1-detailed}

\noindent\textbf{Use Case Name:} Form a cluster

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to pool the available computers into one cluster
    with little effort and to see what the cluster contains.
    \item Device Owner: wants no device to take part without the owner's
    consent.
    \item Inference User: wants a working cluster to send prompts to.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item Lake client is installed on every computer the operator wants to use.
    \item The computers are on the same local network.
    \item The operator can open the Lake web user interface on one computer.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item A cluster exists containing the operator's computer (the leader
    node) and every selected computer whose owner confirmed.
    \item The cluster view shows each member's memory and platform.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item No computer is in the cluster without its owner's confirmation.
    \item Computers that did not join are unaffected and keep running as
    before.
    \item The leader node's interface displays the error to the user.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator starts the Lake client on each computer they want to use.
    \item On one of them, the operator opens the Lake client, and that computer becomes
    the leader node.
    \item Client lists the other computers on the network that are running
    Lake client.
    \item The operator selects the computers to include.
    \item Lake client asks each selected computer's owner to confirm
    (\hyperref[UC2]{UC2}).
    \item Lake client shows the cluster with each computer's memory and platform.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{3a.} No other computers running Lake client are found: Lake client informs
    the operator that none were found and that the operator can start Lake client on
    other computers and refresh the list.
    \item \textbf{5a.} An owner declines: that computer is left out of the
    cluster and the operator is told which ones declined
    (\hyperref[UC2]{UC2}).
    \item \textbf{5b.} An owner does not respond: the request ends after a
    timeout, the computer is left out, and the operator is notified.
    \item \textbf{5c.} A selected computer becomes unreachable before it
    confirms: it is left out and the operator is notified.
    \item \textbf{6a.} No computer confirmed: the cluster contains only the
    leader node and the operator is notified.
\end{itemize}

\noindent\textbf{Justification:} This is the first step of any session with the
system and is required to happen before any other actions can take place. It also
validates that Lake will have consent confirmation from each of the computers in the 
network in advance.
% ---------------------------------------------------------------------------
\subsubsection*{UC2: Confirm a device joining}\label{sec:uc2-detailed}

\noindent\textbf{Use Case Name:} Confirm a device joining

\noindent\textbf{Primary Actor:} Device Owner

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Device Owner: decides whether their computer's memory, compute, and
    bandwidth are used, and wants to see what it is doing afterwards.
    \item Operator: needs to know which computers actually joined.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item Lake client is running on the owner's computer.
    \item An operator has selected the computer for a cluster, either when
    forming one (\hyperref[UC1]{UC1}) or during a session
    (\hyperref[UC6]{UC6}).
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item If accepted, the device is a member of the named cluster and its
    owner can see the device's performance and what it is computing.
    \item If declined, the device is not a member.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item The device does not take part in the cluster without an explicit
    acceptance.
    \item The operator is told the outcome for this device.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item A prompt appears on the device asking whether it may join the
    named cluster.
    \item The owner accepts.
    \item The device joins the cluster.
    \item The owner can see what the device is doing for the cluster.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The owner declines: the device is left out of the
    cluster and the operator is notified.
    \item \textbf{2b.} The owner does not respond: the request expires, the
    device is left out, and the operator is notified.
    \item \textbf{2c.} The owner is not at the device or the device is
    asleep: the device is treated as unavailable and left out.
\end{itemize}

\noindent\textbf{Justification:} Consent is a stated requirement of the
first goal (\hyperref[FR-G4-1-1]{FR-G4-1-1}), and the owner is a direct
stakeholder who may not be the person running the cluster.

% ---------------------------------------------------------------------------
\subsubsection*{UC3: Run a model across the cluster}\label{sec:uc3-detailed}

\noindent\textbf{Use Case Name:} Run a model across the cluster

\noindent\textbf{Primary Actors:} Operator (to load the model); Inference User
(to send prompts)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants a model larger than any one computer can hold to
    load across the cluster.
    \item Inference User: wants a complete, correct response to each prompt,
    streamed as it is generated.
    \item Device Owner: wants their device to hold only its share of the
    model.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster exists (\hyperref[UC1]{UC1}).
    \item The operator has a model file in a supported format
    (GGUF).
    \item The cluster has enough combined memory for the model.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The model is loaded across the cluster, each node holding only its
    assigned layers.
    \item The user receives a complete response to each prompt, and the
    session keeps its context for further prompts.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the model cannot be loaded, the operator is notified including a reason why.
    \item A partial response from the device network is identified as such with a warning.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator chooses a model file.
    \item Lake system divides the model among the nodes and each node loads its
    share.
    \item Lake client reports that the model is loaded across the cluster.
    \item A user sends a prompt.
    \item The response streams back to the leader node.
    \item Steps 4 and 5 repeat until the user chooses to stop the session.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{1a.} The chosen file is not a supported model format or is
    unreadable: Lake client rejects it and provides reasoning.
    \item \textbf{2a.} The cluster's combined memory is too small for the
    model: Lake does not start loading, tells the operator why, and says what
    would fix it (for example adding a computer or choosing a smaller
    model).
    \item \textbf{2b.} A node fails while loading its share: Lake treats it
    as a node leaving (\hyperref[UC5]{UC5}).
    \item \textbf{4a.} A prompt arrives before loading has finished: Lake
    notifies the user the model is not ready.
    \item \textbf{5a.} A node leaves while the response is streaming: see
    \hyperref[UC5]{UC5}.
\end{itemize}

\noindent\textbf{Justification:} This is the primary goal of Lake: running a
model that does not fit on any single device.

\subsubsection*{UC4: Use Lake from an existing tool}\label{sec:uc4-detailed}

\noindent\textbf{Use Case Name:} Use Lake from an existing tool

\noindent\textbf{Primary Actor:} Inference User

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference User: wants to keep using the chat interface or coding
    assistant they already use, with no changes to it.
    \item Regulated organisations: want prompts and responses to stay only on the
    local network.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded (\hyperref[UC3]{UC3}).
    \item The user's tool can talk to an OpenAI-format API and can reach the
    leader node over the network.
    \item The user knows the Lake client address.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The tool works in a similar fashion to how it would with a cloud provider.
    \item Prompts and responses pass only through devices on the local
    network.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the request cannot be served, the tool receives an error
    response in the API's format rather than a hung connection.
    \item No request data is sent outside the cluster.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The user opens the chat interface or coding assistant they already
    use.
    \item The user points it at the Lake address instead of a cloud
    provider.
    \item The user uses the tool as before.
    \item Lake receives each prompt, runs it across the cluster, and returns
    the response (streamed if the tool asks for streaming).
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The address is wrong or the leader node is
    unreachable: the tool reports a connection error.
    \item \textbf{3a.} No model is loaded: Lake client returns an error saying so
    instead of waiting.
    \item \textbf{3b.} The tool uses tool calling or another option Lake does
    not support: Lake client returns an error naming the unsupported
    option.
    \item \textbf{4a.} A node leaves during the request: see
    \hyperref[UC5]{UC5}.
\end{itemize}

\noindent\textbf{Justification:} Compatibility with the tools people already
use removes the main adoption barrier and is the main route by which
inference users reach Lake.

% ---------------------------------------------------------------------------
\subsubsection*{UC5: Keep working when a device leaves}\label{sec:uc5-detailed}

\noindent\textbf{Use Case Name:} Keep working when a device leaves

\noindent\textbf{Primary Actor:} Operator (informed by Lake); Inference User
(whose request is affected)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference User: wants the current prompt answered without having to
    resubmit it, and never wants a cut-off answer presented as a complete one.
    \item Operator: wants to know which device left and what actions will be taken.
    \item Device Owner: wants to be able to close or disconnect their device
    at any time.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster with at least two nodes has a model loaded and is
    serving a session.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The model is reassigned across the remaining nodes.
    \item The user's current prompt has been answered, or re-run, without
    being resubmitted.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the remaining nodes cannot hold the model, the operator is told
    why and what would fix it.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item During a session, a computer in the cluster is closed or
    disconnected by its owner.
    \item Lake client detects that the node has left.
    \item Lake client notifies the operator which device left and that it is
    reorganizing.
    \item Lake client reassigns the model's layers across the remaining nodes.
    \item Lake client answers or re-runs the user's current prompt without the user
    resubmitting it.
    \item The session continues on the remaining nodes.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The device fails or loses its connection without
    warning: Lake detects it as in step 2 and continues.
    \item \textbf{4a.} The remaining computers cannot hold the model: Lake
    stops serving, notifies the operator, and provides a potential solution (for example
    adding a computer), and does not leave the session hanging.
    \item \textbf{4b.} The leader node itself leaves: the session cannot
    continue, and the operator must start again from
    \hyperref[UC1]{UC1}.
\end{itemize}

\noindent\textbf{Justification:} Resilience to devices leaving is a key differentiator
between Lake and existing local distributed inference providers.

% ---------------------------------------------------------------------------
\subsubsection*{UC6: Add a device during a session}\label{sec:uc6-detailed}

\noindent\textbf{Use Case Name:} Add a device during a session

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to use a newly available computer without
    restarting the session.
    \item Device Owner: wants to consent before the device joins
    (\hyperref[UC2]{UC2}).
    \item Inference User: wants to continue prompting and benefit from the
    added computer.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster is running a session.
    \item A new computer running Lake client has appeared on the network.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The new computer is a member of the cluster and holds part of the
    model.
    \item The operator sees the new arrangement.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the computer does not join, the cluster and the session continue
    unchanged.
    \item The user's requests are not lost or corrupted by the
    attempt.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator selects a new computer that has appeared on the
    network.
    \item Its owner confirms (\hyperref[UC2]{UC2}).
    \item Lake reorganizes the model's layers to use the new computer.
    \item Lake shows the new device network arrangement.
    \item The user continues with the session including the new device.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The owner declines or does not respond: the computer
    is not added and the session continues unchanged.
    \item \textbf{3a.} Reorganization fails: Lake keeps the previous
    arrangement, tells the operator, and the session continues.
    \item \textbf{3b.} A prompt is in progress during reorganization: Lake
    finishes it or re-runs it without the user resubmitting, and never
    presents a partial answer as complete.
    \item \textbf{5a.} The change in speed is not an improvement: the
    operator can inspect the cluster view (\hyperref[UC7]{UC7}).
\end{itemize}

\noindent\textbf{Justification:} Taking advantage of new devices is a key differentiator
between Lake and existing local distributed inference providers. It allows Lake to improve performance
through dynamic allocation as a session progresses.

% ---------------------------------------------------------------------------
\subsubsection*{UC7: Find the bottleneck}\label{sec:uc7-detailed}

\noindent\textbf{Use Case Name:} Find the bottleneck

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to know why responses are slow and what to change.
    \item Inference User: wants faster responses.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded and has served at least one
    request.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The operator knows which computer or connection is the slowest and
    can decide what to change.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item Viewing measurements does not interrupt or alter the running
    session.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item Responses feel slow, so the operator opens the cluster view.
    \item The view shows how long each computer and each connection takes per
    word generated.
    \item The view marks the slowest computer or connection.
    \item The operator takes action depending on the provided information, ideally improving
    the performance of the network.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} A node is not reporting measurements: the view marks
    it as unavailable.
    \item \textbf{4a.} The operator removes or adds a computer: see
    \hyperref[UC5]{UC5} or \hyperref[UC6]{UC6}.
\end{itemize}

\noindent\textbf{Justification:} Splitting a model over a network can be
slower than one device only, so the operator must see whether pooling is
beneficial and potential areas for improvement.

% ---------------------------------------------------------------------------
\subsubsection*{UC8: Serve several users at once}\label{sec:uc8-detailed}

\noindent\textbf{Use Case Name:} Serve several users at once

\noindent\textbf{Primary Actor:} Inference User (two or more)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference Users: each wants their own response, as fast as if they
    were alone, and wants no other user to see their prompt or answer.
    \item Operator: wants to see when the cluster is busy enough that requests
    queue.
    \item Regulated organisations: want requests kept separate for data privacy.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded (\hyperref[UC3]{UC3}).
    \item Each user's tool can reach the leader node
    (\hyperref[UC4]{UC4}).
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item Every user receives a complete response to their own prompt.
    \item No user's prompt or response is visible to another user.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item A request that cannot be served is queued or returns an error.
    \item One user's request is never visible or lost to another user, requests are
    always isolated between users.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item Two or more users send prompts to the same cluster at the same
    time, from their own tools.
    \item Lake processes the requests concurrently, each at a different
    stage of the model, keeping their state separate.
    \item Each user sees their own response stream back.
    \item Each response arrives roughly as fast as it would have alone.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The cluster is busy enough that further requests
    cannot start immediately: Lake queues them, and the operator sees the
    queue in the cluster view.
    \item \textbf{3a.} A node leaves while several requests are in progress:
    see \hyperref[UC5]{UC5}; each affected request is re-run or reported
    individually.
    \item \textbf{4a.} Responses slow because of load: the operator can
    inspect the cluster view (\hyperref[UC7]{UC7}).
\end{itemize}

\noindent\textbf{Justification:} Serving several users at once is one of the
main advantages of splitting a model by layers, and it is where Lake's
throughput gain is clear.

\subsection{Verification and Acceptance Criteria}\label{subsec:verification-and-acceptance-criteria}

\newcommand{\req}[1]{\hyperref[#1]{#1}}

\subsubsection{Validation}

Validation checks that \progname{} is the right system for its stakeholders,
measured against the goals in the Problem Statement. The team demonstrates the
system at the proof of concept, Revision 0 and final demonstrations, and the
teaching assistant and other reviewers judge it against these goals:
\begin{itemize}
  \item \textbf{Model Parallelization}: a model split across two or more
    nodes produces coherent output (groups 2 and 3 below).
  \item \textbf{Improved Local Performance}: the cluster runs a model that no
    single node can hold (group 3).
  \item \textbf{Cross-Platform Optimization}: a cluster mixing operating
    systems runs a model (group 12).
  \item \textbf{Dynamic Allocation}: the cluster keeps serving requests after
    nodes join and leave, and the reallocation time is recorded (group 6).
  \item \textbf{Concurrent Inference}: the cluster serves at least two users
    at once without their outputs interfering (group 13).
\end{itemize}
A few people who are not on the team also try the system in the usability
session (group 10), to confirm that it is understandable to new users.

\subsubsection{Verification}

Each group below lists the requirements it covers, how they are verified, and
what counts as acceptance. Every requirement in S.2, the Environmental
Requirements and the Safety and Security Requirements belongs to at least one
group.

\begingroup
\raggedright
\begin{enumerate}
  \item \textbf{Partitioning.} \req{FR.S.1.8}, \req{FR.S.2.1},
    \req{FR.S.2.2}, \req{FR.S.2.4}, \req{FR.S.5.4}, \req{NFR.E.2},
    \req{NFR.E.4}, \req{SR1-1}--\req{SR1-3}.\\
    \textit{Method:} unit and property-based tests of the Model Partitioner on
    generated clusters and models; a Web UI test with a model too large for
    the selected devices; a checksum of the model file before and after
    partitioning.\\
    \textit{Acceptance:} every scheme produced is valid by
    Definition~S.9.2.2, leaves at least \textit{MEMORY\_MARGIN} of each node's
    memory free, and uses at least two nodes for distributed inference;
    failure is reported exactly when no such scheme exists, and the Web UI
    shows the error; the model file's checksum is unchanged. For
    \req{FR.S.2.4}, until its
    definition of capability is made measurable: of two nodes with equal
    memory, the one with the higher measured throughput never receives fewer

\subsection{Formalizations}\label{subsec:formalizations}

Two parts of \progname{} are formalized. S.9.2 defines what counts as a
valid partitioning scheme for the model across the cluster, which every other
requirement depends on. S.9.3 specifies, as a finite state machine, how the
system responds when nodes join and leave the cluster. This is the precise
form of the Dynamic Allocation goal.

\subsubsection{Notation}\label{subsubsec:formal-notation}

For integers $a$ and $b$, $a..b = \{\, n \in \mathbb{N} \mid a \le n \le b
\,\}$, which is empty when $a > b$.

$\mathit{leave}(d)$ only for $d \in D$.

\subsubsection{Valid Partitioning Schemes}\label{subsubsec:formal-partitions}

\begin{definition}[Partitioning scheme]\label{def:partition}
A \emph{partitioning scheme} is a finite sequence of partitions
\begin{equation*}
  P = \langle (d_1, a_1, b_1), \dots, (d_k, a_k, b_k) \rangle,
  \qquad k \ge 1,
\end{equation*}
where $d_i$ is a node and $a_i, b_i \in \mathbb{N}$. Partition $i$ consists
of units $a_i..b_i$, runs on node $d_i$, and passes its output to partition
$i+1$. The nodes of $P$ are $\mathit{dev}(P) = \{d_1, \dots, d_k\}$.
\end{definition}

\begin{definition}[Valid partitioning scheme]\label{def:valid}
$P$ is \emph{valid} over cluster $D$, written $P \in \mathcal{V}(D)$, if and
only if:
\begin{enumerate}
  \item[(V1)] $\mathit{dev}(P) \subseteq D$ and $d_i \ne d_j$ for all
    $1 \le i < j \le k$;
  \item[(V2)] $a_1 = 1$ and $b_k = N$;
  \item[(V3)] $a_i \le b_i$ for all $i \in 1..k$;
  \item[(V4)] $a_{i+1} = b_i + 1$ for all $i \in 1..k-1$;
  \item[(V5)] $\sum_{\ell = a_i}^{b_i} m_\ell \le M_{d_i}$ for all
    $i \in 1..k$.
\end{enumerate}
\end{definition}

(V1) gives each node at most one partition. (V2)--(V4) make the partitions
consecutive, non-empty blocks of units in execution order. (V5) says each
node has room for its partition. The Model Partitioner must return a member
of $\mathcal{V}(D)$ whenever $\mathcal{V}(D) \ne \emptyset$, and must report
failure otherwise (\hyperref[FR.S.2.2]{FR.S.2.2}).

\begin{lemma}[Exact cover]\label{lem:cover}
If $P \in \mathcal{V}(D)$, every unit $\ell \in L$ belongs to exactly one
partition. That is, the sets $a_i..b_i$ for $i \in 1..k$ are non-empty,
pairwise disjoint, and their union is $L$.
\end{lemma}
\begin{proof}
Let $b_0 = 0$. By (V2) and (V4), $a_i = b_{i-1} + 1$ for all $i \in 1..k$,
so partition $i$ consists of units $(b_{i-1}+1)..b_i$. By (V3) these sets are
non-empty, so $0 = b_0 < b_1 < \dots < b_k = N$. Each $\ell \in L$ therefore
satisfies $b_{i-1} < \ell \le b_i$ for exactly one $i$, so it belongs to
exactly one partition.
\end{proof}

\subsubsection{Allocation State Machine}\label{subsubsec:formal-fsm}

The system's response to nodes joining and leaving the cluster is a finite
state machine $(Q, \Sigma, \delta, q_0)$ whose transitions are guarded by
predicates over the cluster $D$ and the active partitioning scheme $P$.

\paragraph{States.}
$Q = \{\mathsf{U}, \mathsf{A}, \mathsf{I}, \mathsf{G}, \mathsf{R},
\mathsf{X}\}$ with $q_0 = \mathsf{U}$:
\begin{itemize}
  \item $\mathsf{U}$ (Unloaded): no model is loaded.
  \item $\mathsf{A}$ (Allocating): a target scheme $P'$ is being loaded, and
    no request is in progress.
  \item $\mathsf{I}$ (Idle): the model is loaded on scheme $P$.
  \item $\mathsf{G}$ (Generating): a request is being served on $P$.
  \item $\mathsf{R}$ (Recovering): a node in $\mathit{dev}(P)$ left during a
    request. The request is stopped while $P'$ is loaded, then retried
    (\hyperref[FR.S.1.13]{FR.S.1.13}).
  \item $\mathsf{X}$ (Insufficient): $\mathcal{V}(D) = \emptyset$, so the
    cluster cannot hold the model.
\end{itemize}

\paragraph{Events.}
$\Sigma = \{\mathit{load}, \mathit{unload}, \mathit{req}, \mathit{fin},
\mathit{done}\} \cup \{\mathit{join}(d), \mathit{leave}(d)\}$:
\begin{itemize}
  \item $\mathit{load}$ and $\mathit{unload}$: the user creates a cluster
    with a model, or shuts it down.
  \item $\mathit{req}$ and $\mathit{fin}$: a request is submitted, or
    finishes.
  \item $\mathit{done}$: the system finishes loading $P'$.
  \item $\mathit{join}(d)$: a device the user selected confirms
    participation and is added to the cluster.
  \item $\mathit{leave}(d)$: follower $d$ leaves, or is detected as failing
    (\hyperref[FR.S.1.10]{FR.S.1.10}).
\end{itemize}
This finite state machine only models the behaviour of follower nodes. If the leader node is detected as
failed (\hyperref[FR.S.1.24]{FR.S.1.24}), the followers shut down and the session ends
(\hyperref[FR.S.1.25]{FR.S.1.25}), which has the same effect as $\mathit{unload}$.

\paragraph{Guards.}
Let $D'$ be the cluster after the event: $D \cup \{d\}$ for
$\mathit{join}(d)$, $D \setminus \{d\}$ for $\mathit{leave}(d)$, and $D$
otherwise. Then
\begin{equation*}
  \varphi \;\equiv\; \mathcal{V}(D') \ne \emptyset
  \qquad\text{and}\qquad
  \psi \;\equiv\; d \in \mathit{dev}(P).
\end{equation*}
Whenever the machine enters $\mathsf{A}$ or $\mathsf{R}$, it selects a new
target $P' \in \mathcal{V}(D')$.

\paragraph{Transitions.}
Table~\ref{tab:fsm} defines $\delta$. Combinations it does not list are
handled as follows:
\begin{itemize}
  \item $\mathit{unload}$ moves every state to $\mathsf{U}$ and aborts any
    request in progress.
  \item $\mathit{leave}(d)$ with $\neg\psi$ in $\mathsf{I}$ or $\mathsf{G}$
    removes $d$ from $D$ and leaves the state unchanged.
  \item $\mathit{req}$ is rejected with an error in $\mathsf{U}$ and
    $\mathsf{X}$. $\mathit{req}$ in $\mathsf{A}$, $\mathsf{G}$ or
    $\mathsf{R}$, and $\mathit{join}(d)$ in $\mathsf{G}$ or $\mathsf{R}$, are
    queued and fire in arrival order once $\mathsf{I}$ is entered. The
    machine therefore serves one request at a time, and concurrent requests
    (\hyperref[FR.S.1.14]{FR.S.1.14}) are not modelled.
  \item Any other combination leaves the state unchanged.
\end{itemize}

\begin{table}[H]
\centering
\caption{Transition function $\delta$ of the allocation state machine}
\label{tab:fsm}

\begin{tabularx}{\textwidth}{|c|c|l|c|>{\raggedright\arraybackslash}X|}
\hline
\textbf{\#} & \textbf{State} & \textbf{Event [guard]} & \textbf{Next} &
\textbf{Effect} \\
\hline
1 & $\mathsf{U}$ & $\mathit{load}$ $[\varphi]$ & $\mathsf{A}$ & Start loading $P'$. \\
2 & $\mathsf{U}$ & $\mathit{load}$ $[\neg\varphi]$ & $\mathsf{X}$ & Report a partitioning failure. \\
\hline

$\mathit{dev}(P)$ keeps $P$ valid.

\paragraph{Invariant.} In states $\mathsf{I}$ and $\mathsf{G}$,
$P \in \mathcal{V}(D)$. $P$ is only assigned in rows 3 and 13, from a $P'$
that is reselected after every change to the cluster. The only change that
keeps the machine in $\mathsf{I}$ or $\mathsf{G}$ removes a node outside
$\mathit{dev}(P)$.

\subsection{Likely Changes to Requirements}\label{subsec:likely-changes-to-requirements}
\begin{itemize}
	\item \label{LC.1}\textbf{LC.1} A Lake cluster cannot recover from a failing leader node (see \hyperref[FR.S.1.25]{FR.S.1.25}).
		In the future, the ability to recover from a failing leader node may be added.
	\item \label{LC.2}\textbf{LC.2} Lake only supports desktop operating systems (Windows, macOS, Linux) (see \hyperref[NFR.S.13]{NFR.S.13}).
		Support for mobile devices (iOS, Android) may be added once other goals and requirements have been met.
	\item \label{LC.3}\textbf{LC.3} Lake assumes the local area network being used to connect the devices is private
		and trusted (See Hazard Analysis Section 4 - Critical Assumptions). Lake's may be extended with additional
		security hardening to allow clusters to run on public or untrusted networks.
	\item \label{LC.4}\textbf{LC.4} Lake requires that each device manually confirm joining a cluster
		(see \hyperref[FR.S.1.17]{FR.S.1.17} and \hyperref[FR.S.1.21]{FR.S.1.21}). In the future,
		a trust mechanism may be introduced, which would allow devices to automatically join clusters created by trusted
		devices without requiring confirmation.
	\item \label{LC.5}\textbf{LC.5} Requirement thresholds and intervals will likely change, as real-world usage
		gives better estimates for reasonable threshold values.
	\item \label{LC.6}\textbf{LC.6} It is likely that future versions of Lake will support a headless mode
		where all UI interactions are performed through a command line interface. This would be useful for users wishing to
		use headless servers as nodes.
\end{itemize}

\subsection{Unlikely Changes to Requirements}\label{subsec:unlikely-changes-to-requirements}
\begin{itemize}
	\item \label{UC.1}\textbf{UC.1} Model training and fine-tuning support is unlikely to be added to Lake. Lake is
		primarily an inference framework, so the addition of training would be out of scope for such a project.
	\item \label{UC.2}\textbf{UC.2} Additional input model formats aside from GGUF (TODO: glossary) are unlikely to
		be added, as GGUF is one of the most common standards for LLMs (TODO: glossary). Additionally, models
		in other formats can be converted to GGUF so there is little reason for Lake to support them directly.
	\item \label{UC.3}\textbf{UC.3} A primary goal of Lake is privacy (see \hyperref[NFR.S.11]{NFR.S.11}),
		so modifications that would compromise privacy like incorporating cloud-based services are unlikely.
	\item \label{UC.4}\textbf{UC.4} Even though one of Lake's goals is to run larger models, integrating quantization
		tools into Lake is unlikely. Lake's scope is focused on distributed inference, and quantization tools
		would better fit in the scope of an independent project.
\end{itemize}

\subsection{Required Technology Elements}\label{subsec:required-tech}

\begin{itemize}
    \item \textbf{Primary Programming Language} - The primary programming languages for the 
    system will be Python and Rust. Python is chosen due to its common use for artificial intelligence applications
    and rich library ecosystem. Rust is chosen due to its high performance and type safety, along with it being a common choice for
    working directly with tensors. On each node, Python will be used for coordinator operations and Rust will be used for the inference engine. 
    User interface will be created using TypeScript due to it being an industry standard type safe language for user interfaces.
    \item \textbf{Communication Framework} - gRPC is a remote procedure call framework
    developed by Google. It allows a client to call a method directly on a server and prioritizes speed and performance.
    \item \textbf{Inference Engine} - llama.cpp is an open-source LLM inference engine. It allows users to run large language models locally on consumer hardware. It was selected due
    to its ubiquity in the open-source AI field.
    \item \textbf{Machine Learning / Tensor Library} - ggml is a standard open-source library for machine learning inference on consumer hardware. Its focus on simplicity and broad
    backend support (across multiple kernels and platforms) is why the team selected it.
    \item \textbf{Model File Format} - gguf is directly compatible with llama.cpp and ggml, so will be used as the format for transporting model layers from one device to another.
    \item \textbf{Frontend Framework} Next.js with TypeScript and Vite as the build tool. This is what the team is familiar with and aligns with the earlier choice for TypeScript as the 
    frontend language.
    \item \textbf{Hardware} Multiple $(>=2)$ laptop or personal computer devices that can be connected via Thunderbolt to run local inference tests.
    \item \textbf{Version Control} Git, along with GitHub for source code management.
    \item \textbf{Continuous Integration} GitHub Actions for build pipelines and testing.
    \item \textbf{Testing API and Interface} OpenAI API Interface will be used for testing the system without using the user interface (or prior to building the user interface). 
\end{itemize}

\subsection{Risk and Mitigation Analysis}\label{subsec:risk}

\begin{itemize}
    \item \textbf{Risk: Lack of Performance Improvement when parallelizing a model}
    \begin{itemize}
        \item Description: This project focuses on the potential improvements of parallelizing
        a model across a pool of devices. If in testing it is determined that splitting up a model
        is not yielding considerably better results in terms of speed or model benchmarks, the system
        may lose users.
        \item Mitigation: Place additional focus on prioritizing privacy of data and size of model that can be split
        up across a pool. This shifts the project's selling points from speed to privacy and quality and still achieves
        the original project goal.
    \end{itemize}
    \item \textbf{Risk: Chosen Communication Technology (gRPC) fails to meet project needs}
    \begin{itemize}
        \item Description: In the case gRPC does not meet project needs, the team's original strategy for inter-device communication will fail.
        \item Mitigation: Perform initial research and record alternative options. Also research the core technology behind these libraries so that the team can
        make adaptations to fit a library to the project.
    \end{itemize}
    \item \textbf{Risk: User Interface is Unclear}
    \begin{itemize}
        \item Description: The user is unable to tell which devices are being used, or feedback about the device network
        is unclear to the user.
        \item Mitigation: Ensure that user testing and observation is completed by the team prior to the final delivery. This
        should be done by people unfamiliar with the product to ensure that controls and feedback are intuitive and easy to learn.
    \end{itemize}
    \item \textbf{Risk: External Deliverables and Constraints Impacting Timeliness and Quality of Project Work}
    \begin{itemize}
        \item Description: Due to various other commitments including work, other courses, and extra-curriculars, team members may not be able to complete high quality project work and deliverables on-time.
        \item Mitigation: At the first meeting for a deliverable, the team will allocate tasks and assign issues to each member so workload is clear.
        As the team progresses through the deliverable, they may adjust the workload as needed, however should aim for an even split over the course of the project.
        The team will also establish an extended review meeting to conduct prior to deliverable hand-off to ensure it aligns with the rubric, the requirements,
        and their own quality standard.
    \end{itemize}
    
\end{itemize}

\begin{itemize}
    \item \label{SR0-1}\textbf{SR0-1} -- The system shall identify and discard stale device health data from determining device availability by configuring a time-to-live for valid data. 
    \item \label{SR0-2}\textbf{SR0-2} -- The system shall only route inference requests to nodes that currently have a confirmed model layer partition.
    \item \label{SR1-1}\textbf{SR1-1} -- The system shall assign at least two nodes for model layer partitioning during distributed inference.
    \item \label{SR1-2}\textbf{SR1-2} -- The system shall ensure all model layers are assigned to a node, and that each device configured to run model layers receives a non-zero model layer partition assignment.
    \item \label{SR1-3}\textbf{SR1-3} -- The system shall reject models and layer allocations that are estimated to exceed the memory capacities of the Lake network or individual nodes, including a configured safety margin. Related SRS requirements: FR.S.2.1, FR.S.2.2.
    \item \label{SR2-1}\textbf{SR2-1} -- The system shall attempt an automatic bounded recovery and retry on inference requests if a follower node fails during inference. If the follower node is unable to be recovered within the configured recovery limits, the system must report to the API that the request has failed. Related SRS requirements: FR.S.1.10, FR.S.1.11, FR.S.1.13.
    \item \label{SR3-1}\textbf{SR3-1} -- The system shall identify corrupted and incomplete tensors throughout the distributed inference with integrity checks and communication timeouts to discard affected data and retry requests.
    \item \label{SR3-2}\textbf{SR3-2} -- The system shall log failed tensor decoding metadata and report a failure to the coordinator so the inference request can recover, subject to SR5-2.
    \item \label{SR4-1}\textbf{SR4-1} -- The system shall configure a timeout for communication between nodes, and handle exceeded timeouts according to the appropriate recovery or failure policy.
    \item \label{SR4-2}\textbf{SR4-2} -- The system shall mark a node as unavailable for inference or model layer partitioning when the node health criteria are not met, and require a successful health check before marking the same node as available. During a leader node failure, follower nodes shall detect and initiate a shutdown. Related SRS requirements: FR.S.1.24 and FR.S.1.25.
    \item \label{SR4-3}\textbf{SR4-3} -- The system shall utilize configured values or historical data to determine a baseline inter-node communication latency and notify the coordinator when that baseline is exceeded by a specified tolerance.
    \item \label{SR5-1}\textbf{SR5-1} -- The system shall require user approval on the leader node to authorize a follower node, and user confirmation on the follower node to confirm the authorization before it can participate in the Lake network. Related SRS requirements: FR.S.1.17, FR.S.1.18, FR.S.1.20, FR.S.1.21, NFR.S.12.
    \item \label{SR5-2}\textbf{SR5-2} -- The system shall not record prompts, responses, tensor data, and KV cache content in diagnostic logs. Related SRS requirements: NFR.S.10.
\end{itemize}

\section{Appendix --- User Interview}\label{app:interview}

The questions below were sent, on October 16, 2026, to an AI developer at an
aerospace engineering firm who runs the firm's in-house LLM assistant on its
own hardware, and he answered in writing. The answers are summarised; the
full notes are kept with the team's records. How they shaped the Goals chapter is described in
Section~\ref{subsubsec:g7-sources}.

\begin{enumerate}
    \item \emph{What do you use to run models locally today, and on what
    machine?} vLLM for the main models, Ollama for small vision models, and a
    text-embeddings server, all in Docker on Linux, on two GPU workstations
    with 96~GB and 48~GB cards. The main model is a 27-billion parameter
    model at full precision with a 131k-token context.
    \item \emph{What stops you from running a bigger model?} Memory per
    card: the 27B model fills most of a 96~GB card once conversation context
    is added, and a 70B-class model would need both cards or compression.
    Also prompt-reading time on long agent prompts, and leaving room for
    concurrent users. Model quality is already good enough for their tasks.
    \item \emph{Do you have idle computers, and would you pool them?} Most
    office machines are laptops with integrated graphics; some GPU
    workstations sit idle at night. Yes for background jobs (re-indexing,
    OCR, embeddings, overnight test runs); probably not for live chat, since
    a split over the office network would likely be slower than one good
    GPU. Conditions: data control on every machine, backing off instantly
    when the owner is working, tolerance for machines sleeping or updating,
    network speed, and IT approval with signed installers and an off switch.
    \item \emph{If responses were slow, what would you want to see?} A
    per-request timeline per device with the slowest highlighted, per-link
    bandwidth and latency, a comparison against the single best machine,
    whether the prompt cache was hit, and metrics on by default and
    exportable.
    \item \emph{If a machine dropped out mid-answer?} Retry quietly once,
    continuing from where it stopped; if that fails, tell the user and show
    what was written so far. Never return a cut-off answer that looks
    complete, and never repeat an action, since their agent drafts emails
    and edits files. Log every drop-out and remove machines that keep
    failing.
    \item \emph{How much does keeping data on your network matter?} It is
    the reason they run locally: cloud models cannot legally process
    export-controlled documents. Anything like Lake must run fully offline
    with no telemetry, encrypt traffic between nodes, accept only
    company-managed machines, and be auditable. Shared or public networks:
    no.
    \item \emph{Which tools would you use it from?} An OpenAI-compatible
    API is a must, with streaming, tool calling, strict JSON output, image
    input, and options such as turning ``thinking'' off. Then a chat window,
    a coding assistant for code that cannot go to the cloud, and batch
    scripts.
    \item \emph{Command line or installer and UI?} Command line and Docker
    on servers, with configuration in files and pinned versions. On
    colleagues' machines, a signed installer pushed by IT, running as a
    background service with a pause switch. A small admin page for machine
    health and timing. No automatic updates.
\end{enumerate}
