\pegschapter{S}{System}

\subsection{Components}\label{subsec:components}
\begin{figure}[H]
    \centering
	\adjustbox{center}{\includegraphics[width=1.4\textwidth]{component_diagram.png}}
    \caption{Component diagram.}
    \label{fig:component-diagram}
\end{figure}

\begin{itemize}
	\item \textbf{Coordinator} -- This component exists on all nodes,
		but the following responsibilities are only run on the leader node:
		\begin{itemize}
			\item Providing an OpenAI-API compatible API to the user for use with tools like
				\href{https://opencode.ai/}{OpenCode}.
			\item Tracking cluster health, and detecting node failures.
			\item Notifying nodes of partitioning changes.
			\item Rebuilding the cluster and saving in-progress requests
				in the case of node failure, removal, or addition.
			\item Measuring node connection performance.
		\end{itemize}
		On a follower node, it is primarily responsible for managing the inference engine
		on its device, following the instructions of the leader node.

	\item \textbf{Model Partitioner} --
		This component determines how to partition the model among the participating devices. It
		decides at which points to cut the graph, how large each partition is, and which device gets
		each partition. This component is integral to ensuring that each device is assigned an appropriate
		partition given the device's computational and networking performance.

	\item \textbf{Inference Engine} --
		This component is the high-performance inference engine running on each device. It will handle
		execution of the given model partition for each device. It will call into
		\href{https://github.com/ggml-org/ggml}{ggml} using the Rust-to-C FFI to control the execution of a
		device's model partition.

	\item \textbf{Tensor I/O} --
		This component handles the compressing, sending, receiving, and decompressing of tensors between devices.
		It will leverage \href{https://grpc.io/}{gRPC} for high-performance communication, with the potential
		to use a custom solution should \href{https://grpc.io/}{gRPC} fail to meet our requirements in practice.

	\item \textbf{Web UI} --
		This component handles displaying cluster information and structure to the user, as well as allowing user
		inputs to configure a new cluster, or modify an existing cluster.
\end{itemize}

\subsection{Functionality}\label{subsec:functionality}
\subsubsection{Coordinator}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.1.1}\textbf{FR.S.1.1} The system shall provide the local Inference Engine with the model partition
		assigned to the local device.
	\item \label{FR.S.1.2}\textbf{FR.S.1.2} The system shall collect device health/performance
		information\footnote{e.g. token throughput, end-to-end partition latency, backpressure.}
		from the local Inference Engine on a 5 second interval.
		Partially satisfies hazards H0-1 and H0-2 from the Hazard Analysis.
	\item \label{FR.S.1.3}\textbf{FR.S.1.3} The system shall collect the network health/performance
		information\footnote{e.g. RTT, throughput, backpressure.}
		for established connections from the Tensor I/O component on a 5 second interval.
		Partially satisfies hazards H0-1 and H0-2 from the Hazard Analysis.
	\item \label{FR.S.1.4}\textbf{FR.S.1.4} The system shall continuously scan for all other devices on the same network
		running Lake.
	\item \label{FR.S.1.5}\textbf{FR.S.1.5} The system shall provide the upstream and downstream node info to the
		local Tensor I/O.
	\item \textbf{When running on a leader node:}
		\begin{itemize}
			\item \label{FR.S.1.6}\textbf{FR.S.1.6} The system shall send model partitions to other Coordinators on their
				respective devices as determined by the Model Partitioner.
				Partially satisfies hazard H0-2 from the Hazard Analysis.
			\item \label{FR.S.1.7}\textbf{FR.S.1.7} The system shall monitor cluster performance by gathering performance
				data from each follower node's Coordinator.
				Partially satisfies hazards H0-1 and H0-2 from the Hazard Analysis.
			\item \label{FR.S.1.8}\textbf{FR.S.1.8} The system shall provide the Model Partitioner with the available nodes,
				and gathered node performance data, to help inform optimal model cut points.
			\item \label{FR.S.1.9}\textbf{FR.S.1.9} The system shall provide an HTTP API matching OpenAI's API.
			\item \label{FR.S.1.10}\textbf{FR.S.1.10} The system shall detect failing follower
				nodes\footnote{A "failing" device is defined as severely degraded ($<50\%$ of historical)
				token throughput, whether it be due to network or device resource instability.}.
				Partially satisfies hazards H2-1, H4-2 and H4-1 from the Hazard Analysis.
			\item \label{FR.S.1.11}\textbf{FR.S.1.11} The system shall rebuild the cluster on a node failing or leaving.
				Partially satisfies hazards H2-1, H4-2 and H4-1 from the Hazard Analysis.
			\item \label{FR.S.1.12}\textbf{FR.S.1.12} The system shall rebuild the cluster on a node joining.
			\item \label{FR.S.1.13}\textbf{FR.S.1.13} The system shall retry in-progress requests after a cluster rebuild.
			\item \label{FR.S.1.14}\textbf{FR.S.1.14} The system shall accept multiple concurrent requests through the HTTP API.
				Related to \hyperref[NFR.S.5]{NFR.S.5}.
			\item \label{FR.S.1.15}\textbf{FR.S.1.15} The system shall communicate the cluster graph structure to each follower.
			\item \label{FR.S.1.16}\textbf{FR.S.1.16} The system shall provide the Web UI with cluster information, and
				accept cluster configuration instructions from the Web UI.
			\item \label{FR.S.1.17}\textbf{FR.S.1.17} The system shall not begin inference until all selected followers have
				confirmed participation. Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.18}\textbf{FR.S.1.18} The system shall only include selected followers in a new cluster.
				Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
		\end{itemize}
	\item \textbf{When running on a follower node:}
		\begin{itemize}
			\item \label{FR.S.1.19}\textbf{FR.S.1.19} The system shall accept model partition assignments from the
				leader node Coordinator.
			\item \label{FR.S.1.20}\textbf{FR.S.1.20} The system shall, upon receiving an invite to join a cluster,
				request that the user confirm or decline participation. Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.21}\textbf{FR.S.1.21} The system shall not partake in a cluster without user confirmation.
				Satisfies \hyperref[NFR.S.12]{NFR.S.12}.
			\item \label{FR.S.1.22}\textbf{FR.S.1.22} The system shall not require confirmation to re-join a rebuilding cluster
				led by the same device, so long as the local device was already participating in the original cluster.
			\item \label{FR.S.1.23}\textbf{FR.S.1.23} The system shall report collected health/performance data to the
				leader node Coordinator on a 5 second interval.
				Partially satisfies hazards H0-1 and H0-2 from the Hazard Analysis.
			\item \label{FR.S.1.24}\textbf{FR.S.1.24} The system shall assume the leader node has failed if there has been
				no health query from the leader node for more than 60 consecutive seconds.
			\item \label{FR.S.1.25}\textbf{FR.S.1.25} The system shall initiate the shutdown of the local node, if the leader
				node is assumed to have failed. Partially satisfies hazards H4-2 and H4-1 from the Hazard Analysis.
				\begin{quote}
					\textbf{Rationale:} The Leader node is the device the user is physically using to interact with the cluster,
					so failure of that device will remove the user's ability to use the cluster, whether or not the cluster survives.
					The architecture of Lake will allow the ability to recover from a leader failure to be implemented at a later date.
				\end{quote}
		\end{itemize}
\end{itemize}

\subsubsection{Model Partitioner}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.2.1}\textbf{FR.S.2.1} The system shall assign all devices a partition smaller than their available
		GPU-accessible memory, with additional room left for runtime overhead. Related to \hyperref[NFR.S.4]{NFR.S.4}.
		Satisfies hazard H1-3 from the Hazard Analysis.
	\item \label{FR.S.2.2}\textbf{FR.S.2.2} The system shall report failure in the case that no valid partition across
		the cluster exists (e.g. not enough GPU-accessible memory).
	\item \label{FR.S.2.3}\textbf{FR.S.2.3} The system shall produce partitions that when assembled, are equivalent
		to the original model. Satisfies \hyperref[NFR.S.6]{NFR.S.6}.
	\item \label{FR.S.2.4}\textbf{FR.S.2.4} The system shall assign larger partitions to more capable
		devices\footnote{The "capabilities" of any given devices are defined via a combination of network throughput,
		GPU TFLOPs/TOPs, GPU-accessible memory size, and GPU-accessible memory bandwidth (GB/s).}.
		Related to \hyperref[NFR.S.4]{NFR.S.4}.
\end{itemize}

\subsubsection{Inference Engine}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.3.1}\textbf{FR.S.3.1} The system shall load the model partition given by the local Coordinator into
		GPU-accessible memory.
	\item \label{FR.S.3.2}\textbf{FR.S.3.2} The system shall accept incoming tensors from Tensor I/O, and run them
		through the loaded partition.
	\item \label{FR.S.3.3}\textbf{FR.S.3.3} The system shall send output tensors to Tensor I/O.
	\item \label{FR.S.3.4}\textbf{FR.S.3.4} The system shall measure partition performance
		metrics\footnote{e.g. token throughput, end-to-end partition latency, backpressure.} and provide them to the local
		Coordinator on a 5 second interval.
	\item \label{FR.S.3.5}\textbf{FR.S.3.5} The system shall support processing tensors from multiple different
		requests concurrently. Related to \hyperref[NFR.S.5]{NFR.S.5}.
\end{itemize}

\subsubsection{Tensor I/O}
\textbf{Functional Requirements}
\begin{itemize}
	\item \label{FR.S.4.1}\textbf{FR.S.4.1} The system shall establish connections with neighbouring nodes' Tensor I/O components.
	\item \label{FR.S.4.2}\textbf{FR.S.4.2} The system shall dynamically choose the compression level of
		outgoing tensors to maximize throughput based on available CPU-time and network throughput.
	\item \label{FR.S.4.3}\textbf{FR.S.4.3} The system shall accept input tensors from the upstream node, decompress them,
		and provide them to the Inference Engine.
	\item \label{FR.S.4.4}\textbf{FR.S.4.4} The system shall accept output tensors from the Inference Engine, compress
		them, and send them to the downstream node's Tensor I/O.
	\item \label{FR.S.4.5}\textbf{FR.S.4.5} The system shall measure network performance
		data\footnote{e.g. RTT, throughput, backpressure.}, for established connections, and provide
		that data to the local Coordinator on a 5 second interval.
	\item \label{FR.S.4.6}\textbf{FR.S.4.6} The system shall maintain request association when sending
		tensors\footnote{This is to allow tensors from different concurrent requests to be differentiated.}.
		Related to \hyperref[NFR.S.5]{NFR.S.5}.
\end{itemize}

\subsubsection{Non-Functional Requirements}
\paragraph{Usability}
\begin{itemize}
    \item \label{NFR.S.1}\textbf{NFR.S.1} \textbf{Understandability:} The user must be able to easily understand
		cluster information.
		A new user must be able to describe which devices are participating, the token throughput of the system,
		and which devices/connections are bottlenecks within 2 minutes of seeing the interface.
		Partially satisfied by \hyperref[FR.S.5.4]{FR.S.5.4}, \hyperref[FR.S.5.5]{FR.S.5.5}, and \hyperref[FR.S.5.6]{FR.S.5.6}.
	\item \label{NFR.S.2}\textbf{NFR.S.2} \textbf{Controllability:} The user must be able to easily control
		cluster configuration. A new user must be able to create a new cluster within 2 minutes of seeing the interface.
		Partially satisfied by \hyperref[FR.S.5.1]{FR.S.5.1}, \hyperref[FR.S.5.2]{FR.S.5.2},
		and \hyperref[FR.S.5.3]{FR.S.5.3}.
	\item \label{NFR.S.3}\textbf{NFR.S.3} \textbf{Installability:} The user must be able to easily install Lake
		natively on Windows, macOS, and Linux. On Windows and macOS, the installation process should be automated
		and should require at most 10 clicks after downloading the installer. On Linux, the installation process
		should only require a single package manager command.
\end{itemize}

\paragraph{Performance}
\begin{itemize}
	\item \label{NFR.S.4}\textbf{NFR.S.4} \textbf{Model Size:} The cluster must be able to run a model with more
		parameters, higher precision, or larger context window than would be able to run individually on the
		node with the most memory. Related to \hyperref[FR.S.2.1]{FR.S.2.1}, and
		\hyperref[FR.S.2.4]{FR.S.2.4}.
	\item \label{NFR.S.5}\textbf{NFR.S.5} \textbf{Scalability:} The number of concurrent requests with < 20\%
		individual request performance degradation shall scale linearly with the number of participating devices.
		Related to \hyperref[FR.S.1.14]{FR.S.1.14}, \hyperref[FR.S.3.5]{FR.S.3.5}, and \hyperref[FR.S.4.6]{FR.S.4.6}.
	\item \label{NFR.S.6}\textbf{NFR.S.6} \textbf{Intelligence:} The partitioned model must score at least 95\% as well
		as the same model running on one machine using relevant
		benchmarks\footnote{Relevant benchmarks are entirely dependent on what types of model are being tested.
		Example benchmarks: \href{https://github.com/swe-bench/SWE-bench}{SWE-bench},
		\href{https://epoch.ai/frontiermath}{FrontierMath}}. Satisfied by \hyperref[FR.S.2.3]{FR.S.2.3}.
\end{itemize}

\paragraph{Look and Feel}
\begin{itemize}
	\item \label{NFR.S.7}\textbf{NFR.S.7} \textbf{Consistency:} Colors and fonts must be used consistently
		across the application.
\end{itemize}

\paragraph{Fault-Tolerance}
\begin{itemize}
	\item \label{NFR.S.8}\textbf{NFR.S.8} The system shall reject invalid or corrupted
		\href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF} files, and notify the user of the
		issue.
	\item \label{NFR.S.9}\textbf{NFR.S.9} The system shall produce correct results in the face of network packet
		corruption and dropping up to 10\% packet loss. Partially satisfies hazard H3-1 from the Hazard Analysis.
\end{itemize}

\paragraph{Privacy}
\begin{itemize}
	\item \label{NFR.S.10}\textbf{NFR.S.10} The system shall not save any request
		data\footnote{\textbf{Request data} refers to any data sent to Lake as part of the request, or any data
		that would give insight into what the data sent in the request might have been.}
		after the request has completed.
	\item \label{NFR.S.11}\textbf{NFR.S.11} The system shall not send \textbf{any} data to any device other than those included
		in the cluster. This includes, but is not limited to all kinds of request data, telemetery, and user data.
	\item \label{NFR.S.12}\textbf{NFR.S.12} The system shall not include untrusted devices in
		a cluster. Satisfied by \hyperref[FR.S.1.17]{FR.S.1.17}, \hyperref[FR.S.1.18]{FR.S.1.18},
		\hyperref[FR.S.1.20]{FR.S.1.20}, \hyperref[FR.S.1.21]{FR.S.1.21}, and \hyperref[FR.S.5.7]{FR.S.5.7}.
		Satisfies hazard H5-1 from the Hazard Analysis.
\end{itemize}

\paragraph{Compatibility}
\begin{itemize}
	\item \label{NFR.S.13}\textbf{NFR.S.13} \textbf{Operating System:} The system shall be compatible with Windows, macOS, Linux.
	\item \label{NFR.S.14}\textbf{NFR.S.14} \textbf{CPU Architecture:} The system shall be compatible with x86\_64 and ARM CPU architectures.
	\item \label{NFR.S.15}\textbf{NFR.S.15} \textbf{GPU Technology:} The system shall be compatible with NVIDIA, AMD, and Apple GPUs.
\end{itemize}

\subsection{Interfaces}\label{subsec:interfaces}
Lake requires the following interfaces:
\begin{itemize}
    \item \textbf{OpenAI compatible API} -- An HTTP server, following the OpenAI API structure.
		This will be the API used to interact with the user, via third-party tools of the user's
		choice that accept the OpenAI API (e.g. \href{https://opencode.ai/}{OpenCode}).
	\item \textbf{GGUF input model} -- An input file using the
		\href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF} file format. This contains
		the model Lake will partition and run.
	\item \textbf{Rust-to-C FFI} -- The Rust-to-C foreign function interface will be used to call
		\href{https://github.com/ggml-org/ggml}{ggml} from the Inference Engine.
	\item \textbf{gRPC between nodes} -- A gRPC-based API used to communicate between nodes.
	\item \textbf{REST API between Coordinator and Web UI} -- A REST API for communication between the
		leader Coordinator and the Web UI.
\end{itemize}

\subsection{Normal Operation}\label{subsec:normal-operation}
\begin{enumerate}
	\item User opens Lake instances on all participating machines.
    \item User creates a Lake cluster using the UI on one of the devices, and provides a
		\href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF} file. This
		device becomes the leader node.
	\item Leader node checks connectivity with follower nodes, and collects performance
		metrics for each node.
	\item Partitioner devises a partitioning scheme based on the collected metrics.
	\item Leader node sends the model partitions to their respective devices.
	\item Neighbouring nodes on the partition graph establish direct P2P connections.
	\item User initiates inference request by providing a prompt via the OpenAI compatible
		API.
	\item Leader node sends the prompt tokens to the inference engine corresponding to the
		first node of the graph, initiating prefill.
	\item Prompt tokens propagate through the graph until prefill completes, and the first
		output token is generated.
	\item Output tokens are repeatedly fed back into the top of the graph, generating a new token
		on each iteration until the response is complete.
	\item As the response generates, the user receives the generated output via the OpenAI compatible
		API.
	\item User initiates a shutdown of the Lake cluster.
	\item Each node unloads its portion of the graph.
	\item Leader node saves the cluster configuration to disk.
	\item All nodes sever their connections, and all Lake instances terminate.
\end{enumerate}

\subsection{Undesired Event Handling}\label{subsec:undesired-event-handling}
\begin{itemize}
    \item \textbf{Model is too large for the available memory in the cluster} --
		The Partitioner reports a partitioning failure, and this error is communicated to the
		user via the Web UI.
	\item \textbf{Follower node fails during inference} -- Leader node re-tries inference,
		if it continues to fail, the leader rebuilds the cluster, excluding the problematic device.
		Associated with hazard H2-1 in the Hazard Analysis.
	\item \textbf{Tensors are corrupted on transfer between nodes} -- The receiving Tensor I/O
		requests that the tensor is retransmitted from the source Tensor I/O.
		Associated with hazard H3-1 in the Hazard Analysis.
	\item \textbf{Connection between two nodes is lost} -- The nodes in question attempt to
		re-establish a connection. If this fails, the leader must rebuild the cluster, excluding
		the failed link. Associated with hazard H4-1 in the Hazard Analysis.
	\item \textbf{Input \href{https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}{GGUF}
		file is corrupted or fails to load} --
		Refuse to begin inference, and inform the user of the corrupted or faulty file.
	\item \textbf{A request is made with a larger prompt than the cluster has memory for} --
		If there are existing requests running, wait for them to complete, then try again.
		If there is still not enough memory, return an error for the request, and instruct the user
		to shorten their prompt or context window.
	\item \textbf{A rebuilt cluster is too small to hold the model after a node leaves} --
		The Partitioner reports a partitioning failure, and this error is communicated to the
		user via the Web UI.
	\item \textbf{A user attempts to create a cluster with a node without a GPU} --
		The Web UI displays an error message outlining the requirement for all nodes to have a GPU.
\end{itemize}

\subsection{Detailed Usage Scenarios}\label{subsec:detailed-usage-scenarios}

This section expands each high-level scenario from
Section~\ref{subsec:high-level-usage-scenarios} (UC1--UC8) into a full use
case with preconditions, guarantees, a numbered main success scenario, and
extensions. Step numbers in the extensions refer to the main success
scenario of the same use case.

% ---------------------------------------------------------------------------
\subsubsection*{UC1: Form a cluster}\label{sec:uc1-detailed}

\noindent\textbf{Use Case Name:} Form a cluster

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to pool the available computers into one cluster
    with little effort and to see what the cluster contains.
    \item Device Owner: wants no device to take part without the owner's
    consent.
    \item Inference User: wants a working cluster to send prompts to.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item Lake is installed on every computer the operator wants to use.
    \item The computers are on the same local network.
    \item The operator can open the Lake web user interface on one computer.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item A cluster exists containing the operator's computer (the leader
    node) and every selected computer whose owner confirmed.
    \item The cluster view shows each member's memory and platform.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item No computer is in the cluster without its owner's confirmation.
    \item Computers that did not join are unaffected and keep running as
    before.
    \item The leader node's interface displays the error to the user.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator starts Lake on each computer they want to use.
    \item On one of them, the operator opens Lake, and that computer becomes
    the leader node.
    \item Lake lists the other computers on the network that are running
    Lake.
    \item The operator selects the computers to include.
    \item Lake asks each selected computer's owner to confirm
    (\hyperref[UC2]{UC2}).
    \item Lake shows the cluster with each computer's memory and platform.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{3a.} No other computers running Lake are found: Lake tells
    the operator that none were found and that the operator can start Lake on
    other computers and refresh the list.
    \item \textbf{5a.} An owner declines: that computer is left out of the
    cluster and the operator is told which ones declined
    (\hyperref[UC2]{UC2}).
    \item \textbf{5b.} An owner does not respond: the request ends after a
    timeout, the computer is left out, and the operator is notified.
    \item \textbf{5c.} A selected computer becomes unreachable before it
    confirms: it is left out and the operator is notified.
    \item \textbf{6a.} No computer confirmed: the cluster contains only the
    leader node and the operator is notified.
\end{itemize}

\noindent\textbf{Justification:} This is the first step of any session with the
Lake system and is required to happen before any other actions can take place. It also
validates that Lake will have consent confirmation from each of the computers in the 
network in advance.
% ---------------------------------------------------------------------------
\subsubsection*{UC2: Confirm a device joining}\label{sec:uc2-detailed}

\noindent\textbf{Use Case Name:} Confirm a device joining

\noindent\textbf{Primary Actor:} Device Owner

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Device Owner: decides whether their computer's memory, compute, and
    bandwidth are used, and wants to see what it is doing afterwards.
    \item Operator: needs to know which computers actually joined.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item Lake is running on the owner's computer.
    \item An operator has selected the computer for a cluster, either when
    forming one (\hyperref[UC1]{UC1}) or during a session
    (\hyperref[UC6]{UC6}).
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item If accepted, the device is a member of the named cluster and its
    owner can see the device's performance and what it is computing.
    \item If declined, the device is not a member.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item The device does not take part in the cluster without an explicit
    acceptance.
    \item The operator is told the outcome for this device.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item A prompt appears on the device asking whether it may join the
    named cluster.
    \item The owner accepts.
    \item The device joins the cluster.
    \item The owner can see what the device is doing for the cluster.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The owner declines: the device is left out of the
    cluster and the operator is notified.
    \item \textbf{2b.} The owner does not respond: the request expires, the
    device is left out, and the operator is notified.
    \item \textbf{2c.} The owner is not at the device or the device is
    asleep: the device is treated as unavailable and left out.
\end{itemize}

\noindent\textbf{Justification:} Consent is a stated requirement of the
first goal (\hyperref[FR-G4-1-1]{FR-G4-1-1}), and the owner is a direct
stakeholder who may not be the person running the cluster.

% ---------------------------------------------------------------------------
\subsubsection*{UC3: Run a model across the cluster}\label{sec:uc3-detailed}

\noindent\textbf{Use Case Name:} Run a model across the cluster

\noindent\textbf{Primary Actors:} Operator (to load the model); Inference User
(to send prompts)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants a model larger than any one computer can hold to
    load across the cluster.
    \item Inference User: wants a complete, correct response to each prompt,
    streamed as it is generated.
    \item Device Owner: wants their device to hold only its share of the
    model.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster exists (\hyperref[UC1]{UC1}).
    \item The operator has a model file in a supported format
    (GGUF).
    \item The cluster has enough combined memory for the model.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The model is loaded across the cluster, each node holding only its
    assigned layers.
    \item The user receives a complete response to each prompt, and the
    session keeps its context for further prompts.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the model cannot be loaded, the operator is notified including a reason why.
    \item A partial response from the device network is identified as such with a warning.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator chooses a model file.
    \item Lake divides the model among the nodes and each node loads its
    share.
    \item Lake reports that the model is loaded across the cluster.
    \item A user sends a prompt.
    \item The response streams back to the leader node.
    \item Steps 4 and 5 repeat until the user chooses to stop the session.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{1a.} The chosen file is not a supported model format or is
    unreadable: Lake rejects it provides reasoning.
    \item \textbf{2a.} The cluster's combined memory is too small for the
    model: Lake does not start loading, tells the operator why, and says what
    would fix it (for example adding a computer or choosing a smaller
    model).
    \item \textbf{2b.} A node fails while loading its share: Lake treats it
    as a node leaving (\hyperref[UC5]{UC5}).
    \item \textbf{4a.} A prompt arrives before loading has finished: Lake
    notifies the user the model is not ready.
    \item \textbf{5a.} A node leaves while the response is streaming: see
    \hyperref[UC5]{UC5}.
\end{itemize}

\noindent\textbf{Justification:} This is the primary goal of Lake: running a
model that does not fit on any single device.

% ---------------------------------------------------------------------------
\subsubsection*{UC4: Use Lake from an existing tool}\label{sec:uc4-detailed}

\noindent\textbf{Use Case Name:} Use Lake from an existing tool

\noindent\textbf{Primary Actor:} Inference User

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference User: wants to keep using the chat interface or coding
    assistant they already use, with no changes to it.
    \item Regulated organisations: want prompts and responses to stay only on the
    local network.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded (\hyperref[UC3]{UC3}).
    \item The user's tool can talk to an OpenAI-format API and can reach the
    leader node over the network.
    \item The user knows Lake's address.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The tool works in a similar fashion to how it would with a cloud provider.
    \item Prompts and responses pass only through devices on the local
    network.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the request cannot be served, the tool receives an error
    response in the API's format rather than a hung connection.
    \item No request data is sent outside the cluster.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The user opens the chat interface or coding assistant they already
    use.
    \item The user points it at Lake's address instead of a cloud
    provider.
    \item The user uses the tool as before.
    \item Lake receives each prompt, runs it across the cluster, and returns
    the response (streamed if the tool asks for streaming).
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The address is wrong or the leader node is
    unreachable: the tool reports a connection error.
    \item \textbf{3a.} No model is loaded: Lake returns an error saying so
    instead of waiting.
    \item \textbf{3b.} The tool uses tool calling or another option Lake does
    not support: Lake returns an error naming the unsupported
    option.
    \item \textbf{4a.} A node leaves during the request: see
    \hyperref[UC5]{UC5}.
\end{itemize}

\noindent\textbf{Justification:} Compatibility with the tools people already
use removes the main adoption barrier and is the main route by which
inference users reach Lake.

% ---------------------------------------------------------------------------
\subsubsection*{UC5: Keep working when a device leaves}\label{sec:uc5-detailed}

\noindent\textbf{Use Case Name:} Keep working when a device leaves

\noindent\textbf{Primary Actor:} Operator (informed by Lake); Inference User
(whose request is affected)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference User: wants the current prompt answered without having to
    resubmit it, and never wants a cut-off answer presented as a complete one.
    \item Operator: wants to know which device left and what actions will be taken.
    \item Device Owner: wants to be able to close or disconnect their device
    at any time.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster with at least two nodes has a model loaded and is
    serving a session.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The model is reassigned across the remaining nodes.
    \item The user's current prompt has been answered, or re-run, without
    being resubmitted.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the remaining nodes cannot hold the model, the operator is told
    why and what would fix it.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item During a session, a computer in the cluster is closed or
    disconnected by its owner.
    \item Lake detects that the node has left.
    \item Lake notifies the operator which device left and that it is
    reorganising.
    \item Lake reassigns the model's layers across the remaining nodes.
    \item Lake answers or re-runs the user's current prompt without the user
    resubmitting it.
    \item The session continues on the remaining nodes.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The device fails or loses its connection without
    warning: Lake detects it as in step 2 and continues.
    \item \textbf{4a.} The remaining computers cannot hold the model: Lake
    stops serving, tells the operator why and what would fix it (for example
    adding a computer), and does not leave the session hanging.
    \item \textbf{4b.} The leader node itself leaves: the session cannot
    continue, and the operator must start again from
    \hyperref[UC1]{UC1}.
\end{itemize}

\noindent\textbf{Justification:} Resilience to devices leaving is a key differentiator
between Lake and existing local distributed inference providers.

\subsubsection*{UC6: Add a device during a session}\label{sec:uc6-detailed}

\noindent\textbf{Use Case Name:} Add a device during a session

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to use a newly available computer without
    restarting the session.
    \item Device Owner: wants to consent before the device joins
    (\hyperref[UC2]{UC2}).
    \item Inference User: wants to continue prompting and benefit from the
    added computer.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster is running a session.
    \item A new computer running Lake has appeared on the network.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The new computer is a member of the cluster and holds part of the
    model.
    \item The operator sees the new arrangement.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item If the computer does not join, the cluster and the session continue
    unchanged.
    \item The user's requests are not lost or corrupted by the
    attempt.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item The operator selects a new computer that has appeared on the
    network.
    \item Its owner confirms (\hyperref[UC2]{UC2}).
    \item Lake reorganises the model's layers to use the new computer.
    \item Lake shows the new device network arrangement.
    \item The user continues with the session including the new device.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The owner declines or does not respond: the computer
    is not added and the session continues unchanged.
    \item \textbf{3a.} Reorganisation fails: Lake keeps the previous
    arrangement, tells the operator, and the session continues.
    \item \textbf{3b.} A prompt is in progress during reorganisation: Lake
    finishes it or re-runs it without the user resubmitting, and never
    presents a partial answer as complete.
    \item \textbf{5a.} The change in speed is not an improvement: the
    operator can inspect the cluster view (\hyperref[UC7]{UC7}).
\end{itemize}

\noindent\textbf{Justification:} Taking advantage of new devices is a key differentiator
between Lake and existing local distributed inference providers. It allows Lake to improve performance
through dynamic allocation as a session progresses.

\subsubsection*{UC7: Find the bottleneck}\label{sec:uc7-detailed}

\noindent\textbf{Use Case Name:} Find the bottleneck

\noindent\textbf{Primary Actor:} Operator

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Operator: wants to know why responses are slow and what to change.
    \item Inference User: wants faster responses.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded and has served at least one
    request.
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item The operator knows which computer or connection is the slowest and
    can decide what to change.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item Viewing measurements does not interrupt or alter the running
    session.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item Responses feel slow, so the operator opens the cluster view.
    \item The view shows how long each computer and each connection takes per
    word generated.
    \item The view marks the slowest computer or connection.
    \item The operator takes action depending on the provided information, ideally improving
    the performance of the network.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} A node is not reporting measurements: the view marks
    it as unavailable.
    \item \textbf{4a.} The operator removes or adds a computer: see
    \hyperref[UC5]{UC5} or \hyperref[UC6]{UC6}.
\end{itemize}

\noindent\textbf{Justification:} Splitting a model over a network can be
slower than one device only, so the operator must see whether pooling is
beneficial and potential areas for improvement.

\subsubsection*{UC8: Serve several users at once}\label{sec:uc8-detailed}

\noindent\textbf{Use Case Name:} Serve several users at once

\noindent\textbf{Primary Actor:} Inference User (two or more)

\noindent\textbf{Stakeholders and Interests:}
\begin{itemize}
    \item Inference Users: each wants their own response, as fast as if they
    were alone, and wants no other user to see their prompt or answer.
    \item Operator: wants to see when the cluster is busy enough that requests
    queue.
    \item Regulated organisations: want requests kept separate for data privacy.
\end{itemize}

\noindent\textbf{Preconditions:}
\begin{itemize}
    \item A cluster has a model loaded (\hyperref[UC3]{UC3}).
    \item Each user's tool can reach the leader node
    (\hyperref[UC4]{UC4}).
\end{itemize}

\noindent\textbf{Postconditions (Success Guarantees):}
\begin{itemize}
    \item Every user receives a complete response to their own prompt.
    \item No user's prompt or response is visible to another user.
\end{itemize}

\noindent\textbf{Postconditions (Failure Guarantees):}
\begin{itemize}
    \item A request that cannot be served is queued or returns an error.
    \item One user's request is never visible or lost to another user, requests are
    always isolated between users.
\end{itemize}

\noindent\textbf{Main Success Scenario (Basic Flow):}
\begin{enumerate}
    \item Two or more users send prompts to the same cluster at the same
    time, from their own tools.
    \item Lake processes the requests concurrently, each at a different
    stage of the model, keeping their state separate.
    \item Each user sees their own response stream back.
    \item Each response arrives roughly as fast as it would have alone.
\end{enumerate}

\noindent\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The cluster is busy enough that further requests
    cannot start immediately: Lake queues them, and the operator sees the
    queue in the cluster view.
    \item \textbf{3a.} A node leaves while several requests are in progress:
    see \hyperref[UC5]{UC5}; each affected request is re-run or reported
    individually.
    \item \textbf{4a.} Responses slow because of load: the operator can
    inspect the cluster view (\hyperref[UC7]{UC7}).
\end{itemize}

\noindent\textbf{Justification:} Serving several users at once is one of the
main advantages of splitting a model by layers, and it is where Lake's
throughput gain is clear.

\subsection{Formalizations}\label{subsec:formalizations}

Two parts of \progname{} are formalized. S.9.2 defines what counts as a
valid partitioning scheme for the model across the cluster, which every other

\subsubsection{Valid Partitioning Schemes}\label{subsubsec:formal-partitions}

\begin{definition}[Partitioning scheme]\label{def:partition}
A \emph{partitioning scheme} is a finite sequence of partitions
\begin{equation*}
  P = \langle (d_1, a_1, b_1), \dots, (d_k, a_k, b_k) \rangle,
  \qquad k \ge 1,
\end{equation*}
where $d_i$ is a node and $a_i, b_i \in \mathbb{N}$. Partition $i$ consists
of units $a_i..b_i$, runs on node $d_i$, and passes its output to partition
$i+1$. The nodes of $P$ are $\mathit{dev}(P) = \{d_1, \dots, d_k\}$.
\end{definition}

\begin{definition}[Valid partitioning scheme]\label{def:valid}
$P$ is \emph{valid} over cluster $D$, written $P \in \mathcal{V}(D)$, if and
only if:
\begin{enumerate}
  \item[(V1)] $\mathit{dev}(P) \subseteq D$ and $d_i \ne d_j$ for all
    $1 \le i < j \le k$;
  \item[(V2)] $a_1 = 1$ and $b_k = N$;
  \item[(V3)] $a_i \le b_i$ for all $i \in 1..k$;
  \item[(V4)] $a_{i+1} = b_i + 1$ for all $i \in 1..k-1$;
  \item[(V5)] $\sum_{\ell = a_i}^{b_i} m_\ell \le M_{d_i}$ for all
    $i \in 1..k$.
\end{enumerate}
\end{definition}

(V1) gives each node at most one partition. (V2)--(V4) make the partitions
consecutive, non-empty blocks of units in execution order. (V5) says each
node has room for its partition. The Model Partitioner must return a member
of $\mathcal{V}(D)$ whenever $\mathcal{V}(D) \ne \emptyset$, and must report
failure otherwise (\hyperref[FR.S.2.2]{FR.S.2.2}).

\begin{lemma}[Exact cover]\label{lem:cover}
If $P \in \mathcal{V}(D)$, every unit $\ell \in L$ belongs to exactly one
partition. That is, the sets $a_i..b_i$ for $i \in 1..k$ are non-empty,
pairwise disjoint, and their union is $L$.
\end{lemma}
\begin{proof}
Let $b_0 = 0$. By (V2) and (V4), $a_i = b_{i-1} + 1$ for all $i \in 1..k$,
so partition $i$ consists of units $(b_{i-1}+1)..b_i$. By (V3) these sets are
non-empty, so $0 = b_0 < b_1 < \dots < b_k = N$. Each $\ell \in L$ therefore
satisfies $b_{i-1} < \ell \le b_i$ for exactly one $i$, so it belongs to
exactly one partition.
\end{proof}

\subsubsection{Allocation State Machine}\label{subsubsec:formal-fsm}

The system's response to nodes joining and leaving the cluster is a finite
state machine $(Q, \Sigma, \delta, q_0)$ whose transitions are guarded by
predicates over the cluster $D$ and the active partitioning scheme $P$.

\paragraph{States.}
$Q = \{\mathsf{U}, \mathsf{A}, \mathsf{I}, \mathsf{G}, \mathsf{R},
\mathsf{X}\}$ with $q_0 = \mathsf{U}$:
\begin{itemize}
  \item $\mathsf{U}$ (Unloaded): no model is loaded.
  \item $\mathsf{A}$ (Allocating): a target scheme $P'$ is being loaded, and
    no request is in progress.
  \item $\mathsf{I}$ (Idle): the model is loaded on scheme $P$.
  \item $\mathsf{G}$ (Generating): a request is being served on $P$.
  \item $\mathsf{R}$ (Recovering): a node in $\mathit{dev}(P)$ left during a
    request. The request is stopped while $P'$ is loaded, then retried
    (\hyperref[FR.S.1.13]{FR.S.1.13}).
  \item $\mathsf{X}$ (Insufficient): $\mathcal{V}(D) = \emptyset$, so the
    cluster cannot hold the model.
\end{itemize}

\paragraph{Events.}
$\Sigma = \{\mathit{load}, \mathit{unload}, \mathit{req}, \mathit{fin},
\mathit{done}\} \cup \{\mathit{join}(d), \mathit{leave}(d)\}$:
\begin{itemize}
  \item $\mathit{load}$ and $\mathit{unload}$: the user creates a cluster
    with a model, or shuts it down.
  \item $\mathit{req}$ and $\mathit{fin}$: a request is submitted, or
    finishes.
  \item $\mathit{done}$: the system finishes loading $P'$.
  \item $\mathit{join}(d)$: a device the user selected confirms
    participation and is added to the cluster.
  \item $\mathit{leave}(d)$: follower $d$ leaves, or is detected as failing
    (\hyperref[FR.S.1.10]{FR.S.1.10}).
\end{itemize}
This finite state machine only models the behaviour of follower nodes. If the leader node is detected as
failed (\hyperref[FR.S.1.24]{FR.S.1.24}), the followers shut down and the session ends
(\hyperref[FR.S.1.25]{FR.S.1.25}), which has the same effect as $\mathit{unload}$.

\paragraph{Guards.}
Let $D'$ be the cluster after the event: $D \cup \{d\}$ for
$\mathit{join}(d)$, $D \setminus \{d\}$ for $\mathit{leave}(d)$, and $D$
otherwise. Then
\begin{equation*}
  \varphi \;\equiv\; \mathcal{V}(D') \ne \emptyset
  \qquad\text{and}\qquad
  \psi \;\equiv\; d \in \mathit{dev}(P).
\end{equation*}
Whenever the machine enters $\mathsf{A}$ or $\mathsf{R}$, it selects a new
target $P' \in \mathcal{V}(D')$.

\paragraph{Transitions.}
Table~\ref{tab:fsm} defines $\delta$. Combinations it does not list are
handled as follows:
\begin{itemize}
  \item $\mathit{unload}$ moves every state to $\mathsf{U}$ and aborts any
    request in progress.
  \item $\mathit{leave}(d)$ with $\neg\psi$ in $\mathsf{I}$ or $\mathsf{G}$
    removes $d$ from $D$ and leaves the state unchanged.
  \item $\mathit{req}$ is rejected with an error in $\mathsf{U}$ and
    $\mathsf{X}$. $\mathit{req}$ in $\mathsf{A}$, $\mathsf{G}$ or
    $\mathsf{R}$, and $\mathit{join}(d)$ in $\mathsf{G}$ or $\mathsf{R}$, are
    queued and fire in arrival order once $\mathsf{I}$ is entered. The
    machine therefore serves one request at a time, and concurrent requests
    (\hyperref[FR.S.1.14]{FR.S.1.14}) are not modelled.
  \item Any other combination leaves the state unchanged.
\end{itemize}

\begin{table}[H]
\centering
\caption{Transition function $\delta$ of the allocation state machine}
\label{tab:fsm}

\begin{tabularx}{\textwidth}{|c|c|l|c|>{\raggedright\arraybackslash}X|}
\hline
\textbf{\#} & \textbf{State} & \textbf{Event [guard]} & \textbf{Next} &
\textbf{Effect} \\
\hline
1 & $\mathsf{U}$ & $\mathit{load}$ $[\varphi]$ & $\mathsf{A}$ & Start loading $P'$. \\
2 & $\mathsf{U}$ & $\mathit{load}$ $[\neg\varphi]$ & $\mathsf{X}$ & Report a partitioning failure. \\

Row 7 needs no guard. Conditions (V1)--(V5) refer to $D$ only through
$\mathit{dev}(P) \subseteq D$, so a scheme valid over $D$ stays valid over
$D \cup \{d\}$. For the same reason, removing a node outside
$\mathit{dev}(P)$ keeps $P$ valid.

\paragraph{Invariant.} In states $\mathsf{I}$ and $\mathsf{G}$,
$P \in \mathcal{V}(D)$. $P$ is only assigned in rows 3 and 13, from a $P'$
that is reselected after every change to the cluster. The only change that
keeps the machine in $\mathsf{I}$ or $\mathsf{G}$ removes a node outside
$\mathit{dev}(P)$.

\subsection{Likely Changes to Requirements}\label{subsec:likely-changes-to-requirements}
\begin{itemize}
	\item \label{LC.1}\textbf{LC.1} A Lake cluster cannot recover from a failing leader node (see \hyperref[FR.S.1.25]{FR.S.1.25}).
		In the future, the ability to recover from a failing leader node may be added.
	\item \label{LC.2}\textbf{LC.2} Lake only supports desktop operating systems (Windows, macOS, Linux) (see \hyperref[NFR.S.13]{NFR.S.13}).
		Support for mobile devices (iOS, Android) may be added once other goals and requirements have been met.
	\item \label{LC.3}\textbf{LC.3} Lake assumes the local area network being used to connect the devices is private
		and trusted (See Hazard Analysis Section 4 - Critical Assumptions). Lake's may be extended with additional
		security hardening to allow clusters to run on public or untrusted networks.
	\item \label{LC.4}\textbf{LC.4} Lake requires that each device manually confirm joining a cluster
		(see \hyperref[FR.S.1.17]{FR.S.1.17} and \hyperref[FR.S.1.21]{FR.S.1.21}). In the future,
		a trust mechanism may be introduced, which would allow devices to automatically join clusters created by trusted
		devices without requiring confirmation.
	\item \label{LC.5}\textbf{LC.5} Requirement thresholds and intervals will likely change, as real-world usage
		gives better estimates for reasonable threshold values.
	\item \label{LC.6}\textbf{LC.6} It is likely that future versions of Lake will support a headless mode
		where all UI interactions are performed through a command line interface. This would be useful for users wishing to
		use headless servers as nodes.
\end{itemize}

\subsection{Unlikely Changes to Requirements}\label{subsec:unlikely-changes-to-requirements}
\begin{itemize}
	\item \label{UC.1}\textbf{UC.1} Model training and fine-tuning support is unlikely to be added to Lake. Lake is
		primarily an inference framework, so the addition of training would be out of scope for such a project.
	\item \label{UC.2}\textbf{UC.2} Additional input model formats aside from GGUF (TODO: glossary) are unlikely to
		be added, as GGUF is one of the most common standards for LLMs (TODO: glossary). Additionally, models
		in other formats can be converted to GGUF so there is little reason for Lake to support them directly.
	\item \label{UC.3}\textbf{UC.3} A primary goal of Lake is privacy (see \hyperref[NFR.S.11]{NFR.S.11}),
		so modifications that would compromise privacy like incorporating cloud-based services are unlikely.
	\item \label{UC.4}\textbf{UC.4} Even though one of Lake's goals is to run larger models, integrating quantization
		tools into Lake is unlikely. Lake's scope is focused on distributed inference, and quantization tools
		would better fit in the scope of an independent project.
\end{itemize}

\subsection{Required Technology Elements}\label{subsec:required-tech}

\begin{itemize}
    \item \textbf{Primary Programming Language} - The primary programming languages for the 
    system will be Python and Rust. Python is chosen due to its common use for artificial intelligence applications
    and rich library ecosystem. Rust is chosen due to its high performance and type safety, along with it being a common choice for
    working directly with tensors. On each node, Python will be used for coordinator operations and Rust will be used for the inference engine. 
    User interface will be created using TypeScript due to it being an industry standard type safe language for user interfaces.
    \item \textbf{Communication Framework} - gRPC is a remote procedure call framework
    developed by Google. It allows a client to call a method directly on a server and prioritizes speed and performance.
    \item \textbf{Inference Engine} - llama.cpp is an open-source LLM inference engine. It allows users to run large language models locally on consumer hardware. It was selected due
    to its ubiquity in the open-source AI field.
    \item \textbf{Machine Learning / Tensor Library} - ggml is a standard open-source library for machine learning inference on consumer hardware. Its focus on simplicity and broad
    backend support (across multiple kernels and platforms) is why the team selected it.
    \item \textbf{Model File Format} - gguf is directly compatible with llama.cpp and ggml, so will be used as the format for transporting model layers from one device to another.
    \item \textbf{Frontend Framework} Next.js with TypeScript and Vite as the build tool. This is what the team is familiar with and aligns with the earlier choice for TypeScript as the 
    frontend language.
    \item \textbf{Hardware} Multiple $(>=2)$ laptop or personal computer devices that can be connected via Thunderbolt to run local inference tests.
    \item \textbf{Version Control} Git, along with GitHub for source code management.
    \item \textbf{Continuous Integration} GitHub Actions for build pipelines and testing.
    \item \textbf{Testing API and Interface} OpenAI API Interface will be used for testing the system without using the user interface (or prior to building the user interface). 
\end{itemize}

\subsection{Risk and Mitigation Analysis}\label{subsec:risk}

\begin{itemize}
    \item \textbf{Risk: Lack of Performance Improvement when parallelizing a model}
    \begin{itemize}
        \item Description: This project focuses on the potential improvements of parallelizing
        a model across a pool of devices. If in testing it is determined that splitting up a model
        is not yielding considerably better results in terms of speed or model benchmarks, the system
        may lose users.
        \item Mitigation: Place additional focus on prioritizing privacy of data and size of model that can be split
        up across a pool. This shifts the project's selling points from speed to privacy and quality and still achieves
        the original project goal.
    \end{itemize}
    \item \textbf{Risk: Chosen Communication Technology (gRPC) fails to meet project needs}
    \begin{itemize}
        \item Description: In the case gRPC does not meet project needs, the team's original strategy for inter-device communication will fail.
        \item Mitigation: Perform initial research and record alternative options. Also research the core technology behind these libraries so that the team can
        make adaptations to fit a library to the project.
    \end{itemize}
    \item \textbf{Risk: User Interface is Unclear}
    \begin{itemize}
        \item Description: The user is unable to tell which devices are being used, or feedback about the device network
        is unclear to the user.
        \item Mitigation: Ensure that user testing and observation is completed by the team prior to the final delivery. This
        should be done by people unfamiliar with the product to ensure that controls and feedback are intuitive and easy to learn.
    \end{itemize}
    \item \textbf{Risk: External Deliverables and Constraints Impacting Timeliness and Quality of Project Work}
    \begin{itemize}
        \item Description: Due to various other commitments including work, other courses, and extra-curriculars, team members may not be able to complete high quality project work and deliverables on-time.
        \item Mitigation: At the first meeting for a deliverable, the team will allocate tasks and assign issues to each member so workload is clear.
        As the team progresses through the deliverable, they may adjust the workload as needed, however should aim for an even split over the course of the project.
        The team will also establish an extended review meeting to conduct prior to deliverable hand-off to ensure it aligns with the rubric, the requirements,
        and their own quality standard.
    \end{itemize}
    
\end{itemize}
